## 1. このテストで確かめること

作ったものが**要件どおりに動くか**を、利用者の目で確かめます。
プログラムの内部が正しいかは自動テストが受け持つので、ここでは**画面を操作した結果**を見ます。

### 1.1 テストの種類と受け持ち


| 種類            | 何を確かめるか              | 誰が・いつ                | 状態         |
| ------------- | -------------------- | -------------------- | ---------- |
| ユニットテスト       | Service の計算や判断が正しいか  | 自動（`./gradlew test`） | 実装と同時に作成済み |
| API 結合テスト     | エンドポイントが仕様どおり応答するか   | 自動（`./gradlew test`） | 同上         |
| 画面の部品テスト      | 画面の分岐・文言・送信内容が正しいか   | 自動（`npm test`）       | 同上         |
| **総合テスト（本書）** | **要件が利用者の操作で満たされるか** | **手動。本書の手順で実施**      | **これから実施** |


> 自動テストは「部品が仕様どおりか」を細かく確かめますが、**部品をつないだときに使えるか**は分かりません。
> たとえば「登録ボタンを押しても画面が変わらない」不具合は、部品ごとのテストがすべて通っていても起きました。
> 本書はそこを埋めるためのものです。



### 1.2 本書で確かめないこと


| 対象外                                            | 理由                                                                                                |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| Should / Could の機能（F-36 ラベル、F-37 検索、F-51 書き出し） | バージョン1では作らないため（[01-2 機能要件](01-2_functional-requirements.md)）                                      |
| Chrome 以外のブラウザ、スマートフォン                         | 対応環境の対象外（[要件 6. 非機能要件](01_requirements.md#6-非機能要件)、[05 画面設計書 1章](05_screen-design.md#1-設計方針) 方針4） |
| 30日間のログイン保持の経過確認                               | 30日待てないため。仕組み（Cookie の有効期限）が設定されていることの確認にとどめる                                                     |
| 公開先（Vercel / Render / Neon）での動作                | リリース工程で別途確認する                                                                                     |

## 2. テスト環境


| 項目      | 内容                                                                                                 |
| ------- | -------------------------------------------------------------------------------------------------- |
| ブラウザ    | PC の最新版 Google Chrome（要件 6. 対応環境）                                                                  |
| 画面幅     | 1024px 以上（[05 画面設計書 1章](05_screen-design.md#1-設計方針) 方針4）                                           |
| フロントエンド | `http://localhost:5173`（`cd frontend && npm run dev`）                                              |
| バックエンド  | `http://localhost:8080`（`cd backend && ./gradlew bootRun --args='--spring.profiles.active=local'`） |
| データベース  | Docker の PostgreSQL（リポジトリ直下で `docker compose up -d`）                                               |


> `local` プロファイルを付け忘れると、Cookie の設定（`Secure`・`SameSite=None`）が本番向けのままになり、
> `http://localhost` ではログインできません。必ず付けてください。



### 2.1 始める前の準備

1. `docker compose up -d` でデータベースを起動する
2. バックエンドを起動し、`http://localhost:8080/swagger-ui.html` が開けることを確認する
3. フロントエンドを起動し、`http://localhost:5173` が開けることを確認する
4. Chrome の**シークレットウィンドウ**で開く（前に使ったログイン状態が残っていない状態から始めるため）



### 2.2 テストで使うアカウント


| 名前   | ユーザーID        | パスワード      | 用途                       |
| ---- | ------------- | ---------- | ------------------------ |
| 利用者A | `test_user_a` | `pass1234` | ほとんどの項目で使う               |
| 利用者B | `test_user_b` | `pass1234` | 他人のデータが見えないことの確認（T-I）で使う |


> テストを最初からやり直したいときは、リポジトリ直下で `docker compose down -v` を実行してから
> `docker compose up -d` でデータベースを作り直します（**保存したデータはすべて消えます**）。

## 3. 結果の記録のしかた

各項目の「結果」欄に次のいずれかを書きます。


| 記号  | 意味                                  |
| --- | ----------------------------------- |
| OK  | 期待する結果のとおりだった                       |
| NG  | 期待する結果と違った。「気づいたこと」に**実際に起きたこと**を書く |
| －   | 実施しなかった（理由を書く）                      |


NG があったときは、GitHub の Issue を作って記録します。本書の項目 ID（例：T-D-05）を必ず書いてください。

```markdown
## 起きていること
（T-D-05）カードのタイトルを変更して Enter を押しても、元のタイトルのまま戻る

## 手順
1. …
2. …

## 期待する結果
変更したタイトルで表示される
```
