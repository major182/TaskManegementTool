## 1. 設計方針（先に決めたこと）

| No | 決めたこと | 採用 | 理由 |
|---|---|---|---|
| 1 | ログインセッションの保存先 | **Spring Security の既定（サーバーのメモリ上）** | 設定が不要で最もシンプル。ただし**サーバーの再起動でログアウトされる**制約があるため、要件 5.6・F-08 を実態に合わせて修正しました（下記 1.1） |
| 2 | ボードを開くときの取得 | **1回のリクエストで、リスト・カードを入れ子にして返す** | 画面表示が1往復で済み、リストごとに取得する方式（N+1）の遅さ・表示のずれを避けられる |
| 3 | 移動（D&D）の API | **移動先リストと位置だけを送り、再採番はサーバーが行う** | 送るデータが小さく、並び順の整合性をサーバー側（1トランザクション）で保証できる |
| 4 | 更新の方法 | **PUT で全項目を送る**（下記 3.3） | 「null は削除」と「キー未指定は変更なし」の区別があいまいになる問題を避けられる |
| 5 | エラーの形式 | **RFC 9457 ProblemDetail**（Spring Boot 3 の標準） | 自前でエラー形式を決めずに済み、フロントの処理を1か所にまとめられる |

### 1.1 セッションをメモリに持つことの制約（要件への影響）

Spring Security の既定では、ログイン情報（セッション）はサーバーのメモリ上に置かれます。そのため次のことが起きます。

- 公開先の Render（無料プラン）は、**しばらくアクセスがないとスリープし、次のアクセスで再起動**します
- 再起動するとメモリ上のセッションは消えるため、**利用者は再ログインが必要**になります
- また、新しいバージョンをデプロイしたときも同じく再ログインが必要になります

要件 5.6・F-08 は「最大30日間ログインしたまま」でしたが、これは**守れません**。そこで要件側を次のように修正しました（v0.16 で反映済み）。

| 修正前 | 修正後 |
|---|---|
| ログイン状態は最大30日間保持する | ログイン状態は最大30日間保持する。**ただしサーバーが再起動・スリープしたときは解除され、再ログインが必要になる** |

> 30日間を確実に保持したい場合は、Spring Session JDBC を導入してセッションも PostgreSQL に保存します（テーブルが2つ増えます）。バージョン1では見送り、「機能追加」フェーズの候補とします（下記 8章 No.1）。

## 2. 共通仕様

### 2.1 基本

| 項目 | 内容 |
|---|---|
| ベースURL（開発） | `http://localhost:8080/api` |
| ベースURL（本番） | `https://（Render のドメイン）/api` |
| 形式 | JSON（リクエスト・レスポンスともに `application/json; charset=UTF-8`） |
| 項目名 | **キャメルケース**（例：`dueDate`、`isDone`）。DB のカラムはスネークケース（`due_date`）なので、Spring が変換します |
| 日時 | ISO 8601・UTC の文字列（例：`2026-09-20T12:34:56Z`）。日本時間への変換は画面側で行う |
| 日付（期限日） | `YYYY-MM-DD` の文字列（例：`2026-09-30`）。時刻は持たない |
| 文字数 | [01-3 業務ルール 5.1](01-3_business-rules.md#51-入力のルール) のとおり。サーバー側で Bean Validation により必ず検証する |

### 2.2 認証

| 項目 | 内容 |
|---|---|
| 方式 | セッション方式。ログイン成功時にサーバーが `JSESSIONID` Cookie を返す |
| Cookie の属性 | `HttpOnly` / `Secure` / `SameSite=None`（画面と API のドメインが違うため） |
| フロント側の送信 | `fetch` に **`credentials: 'include'`** を必ず付ける（付けないと Cookie が送られず、常に 401 になる） |
| 未ログイン時 | `/api/auth/**` 以外はすべて **401** を返す。画面はログイン画面（S-02）へ遷移する |
| 他人のデータ | 存在は知らせず **404** を返す（要件 6.1）。「ログイン中の利用者のデータか」を各処理で必ず確認する |

### 2.3 CSRF 対策

Cookie でセッションを持つため、Spring Security の CSRF 対策を有効にします（`CookieCsrfTokenRepository`）。

1. サーバーが `XSRF-TOKEN` という Cookie を返す
2. フロントは **GET 以外**のリクエストで、その値を `X-XSRF-TOKEN` ヘッダーに入れて送る
3. 一致しない場合は **403** を返す

> フロント側で「更新系の通信だけ失敗して 403 になる」ときは、ほぼこのヘッダーの付け忘れです。

### 2.4 CORS

| 項目 | 内容 |
|---|---|
| 許可するオリジン | `http://localhost:5173`（Vite の開発サーバー）、Vercel の公開ドメイン |
| 許可するメソッド | GET / POST / PUT / PATCH / DELETE / OPTIONS |
| 許可するヘッダー | `Content-Type`、`X-XSRF-TOKEN` |
| 資格情報 | `allowCredentials = true`（Cookie を使うため必須）。このとき**オリジンに `*` は使えない** |

### 2.5 HTTPステータスコード

| コード | 意味 | 使う場面 |
|---|---|---|
| 200 OK | 成功（本文あり） | 取得・更新 |
| 201 Created | 作成成功 | 新規登録・ボード／リスト／カードの作成。`Location` ヘッダーを付ける |
| 204 No Content | 成功（本文なし） | 削除・ログアウト |
| 400 Bad Request | 入力が不正 | 文字数超過、空白だけ、形式違反（業務ルール 5.1） |
| 401 Unauthorized | 未ログイン・セッション切れ・ログイン失敗 | ログイン画面へ戻す |
| 403 Forbidden | CSRF トークンの不一致 | ヘッダーの付け忘れ |
| 404 Not Found | 存在しない、または**他人のデータ** | 要件 6.1 |
| 409 Conflict | すでに使われているユーザーID、元に戻せない状態 | 業務ルール 5.3・5.6 |
| 500 Internal Server Error | サーバー側の想定外エラー | 画面には「保存できませんでした」と表示（F-04） |

### 2.6 エラーレスポンスの形式

Spring Boot 3 標準の **ProblemDetail**（RFC 9457）を使います。

```json
{
  "type": "about:blank",
  "title": "Bad Request",
  "status": 400,
  "detail": "入力内容を確認してください",
  "instance": "/api/boards",
  "errors": [
    { "field": "name", "message": "ボード名は50文字以内で入力してください" }
  ]
}
```

- `errors` は入力チェック（400）のときだけ付ける独自の追加項目。画面は該当の入力欄の近くにメッセージを出す（業務ルール 5.1）
- それ以外のエラーは `detail` をそのまま画面に表示できる文言にする

### 3.2 ボード

| メソッド | パス | 機能 | 対応する要件 |

| POST | /api/boards | ボード作成 | F-12 |
| GET | /api/boards/{boardId} | ボード1件＋リスト＋カード（**画面表示用**） | F-02、F-15 |

| メソッド | パス | 機能 | 対応する要件 |
|---|---|---|---|

| PUT | /api/lists/{listId} | リスト名の変更 | F-22 |
| DELETE | /api/lists/{listId} | ゴミ箱へ移動（中のカードごと） | F-23 |
| PATCH | /api/lists/{listId}/move | 並び替え | F-24 |

### 3.4 カード

| メソッド | パス | 機能 | 対応する要件 |
|---|---|---|---|
| POST | /api/lists/{listId}/cards | カード作成（一番下に追加） | F-31 |
| PUT | /api/cards/{cardId} | タイトル・説明文・期限日・完了の更新 | F-32、F-35、F-38 |
| DELETE | /api/cards/{cardId} | ゴミ箱へ移動 | F-33 |
| PATCH | /api/cards/{cardId}/move | 移動（同じリスト内・別のリストへ） | F-34 |

> **なぜ更新が PUT で、移動が PATCH なのか**
> PUT は「その資源の内容を丸ごと置き換える」ため、**全項目を必ず送ります**。こうすると「`dueDate: null` は期限日を消す指示」とはっきり決まります。もし「送られた項目だけ更新する」方式にすると、`null`（消したい）と「キーを送らない」（変えたくない）を Java 側で区別できず、期限日を消せないという不具合が起きます。
> 一方、移動は「内容の置き換え」ではなく**操作**なので、専用のパス（`/move`）を用意しています。

### 3.5 ゴミ箱

| メソッド | パス | 機能 | 対応する要件 |
|---|---|---|---|
| GET | /api/trash | ゴミ箱の一覧（ボード・リスト・カードをまとめて、削除日時の新しい順） | F-41 |
| GET | /api/trash/count | ゴミ箱の件数（サイドバー表示用） | F-41 |
| POST | /api/trash/{type}/{id}/restore | 元に戻す | F-42 |
| DELETE | /api/trash/{type}/{id} | 完全に削除 | F-43 |
| DELETE | /api/trash | ゴミ箱を空にする | F-44 |

`{type}` は `boards` / `lists` / `cards` のいずれかです。

## 4. リクエスト・レスポンスの詳細

### 4.1 POST /api/auth/signup（新規登録）

```json
// リクエスト
{ "username": "taro_123", "password": "pass1234" }
```
```json
// 201 Created
{ "id": 1, "username": "taro_123", "lastOpenedBoardId": null }
```

| 状況 | コード | 本文の `detail` |
|---|---|---|
| ユーザーID が使われている | 409 | このユーザーID は使われています |
| 形式・文字数が不正 | 400 | `errors` に項目ごとのメッセージ |

- パスワードは `BCryptPasswordEncoder` でハッシュ化して保存し、**レスポンスには一切含めません**
- 「パスワード（確認用）」の一致チェックは画面側で行い、API には送りません
- 成功するとセッションが作られ、そのままログイン状態になります（業務ルール 5.6）

### 4.2 POST /api/auth/login（ログイン）

```json
// リクエスト
{ "username": "taro_123", "password": "pass1234" }
```
```json
// 200 OK
{ "id": 1, "username": "taro_123", "lastOpenedBoardId": 12 }
```

| 状況 | コード | 本文の `detail` |
|---|---|---|
| ユーザーID またはパスワードが違う | 401 | ユーザーID またはパスワードが違います |

> **どちらが違うかは知らせません**（業務ルール 5.6）。ユーザーID の存在を調べられてしまうのを防ぐためです。

### 4.3 GET /api/auth/me（ログイン状態の確認）

画面を開いたとき最初に呼び、200 ならメイン画面（S-01）、401 ならログイン画面（S-02）を表示します。

```json
// 200 OK
{ "id": 1, "username": "taro_123", "lastOpenedBoardId": 12 }
```

| 状況 | コード | 本文の `detail` |
|---|---|---|
| 未ログイン・セッション切れ | 401 | ログインの有効期限が切れました。もう一度ログインしてください |

### 4.4 GET /api/boards（ボード一覧・サイドバー用）

作成日の新しい順（業務ルール 5.2）。ゴミ箱に入っているボードは含みません。

```json
// 200 OK
[
  { "id": 12, "name": "学習計画", "createdAt": "2026-09-20T01:00:00Z" },
  { "id": 7,  "name": "個人タスク", "createdAt": "2026-09-18T09:30:00Z" }
]
```

### 4.5 GET /api/boards/{boardId}（画面表示用・入れ子）

ゴミ箱に入っているリスト・カードは含みません。リストは `position` の昇順（左から右）、カードも `position` の昇順（上から下）で返します。

```json
// 200 OK
{
  "id": 12,
  "name": "学習計画",
  "lists": [
    {
      "id": 3,
      "name": "TODO",
      "position": 0,
      "cards": [
        {
          "id": 8,
          "title": "要件定義を書く",
          "description": "01〜01-5 を仕上げる",
          "dueDate": "2026-09-30",
          "isDone": false,
          "position": 0
        },
        {
          "id": 9, "title": "DB設計", "description": null,
          "dueDate": null, "isDone": true, "position": 1
        }
      ]
    },
    { "id": 4, "name": "DOING", "position": 1, "cards": [] }
  ]
}
```

| 状況 | コード |
|---|---|
| 存在しない、または他人のボード | 404 |
| ゴミ箱に入っているボード | 404（ボードの表示には出さないため。業務ルール 5.2） |

> 「期限日を過ぎた未完了カードを色で目立たせる」（F-35）判定は、`dueDate` と `isDone` から**画面側**で行います。サーバーは事実だけを返します。

### 4.7 PUT /api/boards/{boardId}（ボード名の変更）

```json
// リクエスト

```
```json

```

### 4.8 POST /api/boards/{boardId}/lists（リスト作成）

`position` は指定しません。**サーバーがそのボードの一番右**に割り当てます（業務ルール 5.2）。

```json
// リクエスト
{ "name": "DONE" }
```
```json
// 201 Created   Location: /api/lists/5
{ "id": 5, "name": "DONE", "position": 2, "cards": [] }
```

### 4.9 PATCH /api/lists/{listId}/move（リストの並び替え）

```json
// リクエスト（左から何番目に置くか。0 が一番左）
{ "position": 0 }
```
```json
// 200 OK ＝ 並び替え後のボード内リストの順番（再採番の結果）
[
  { "id": 5, "position": 0 },
  { "id": 3, "position": 1 },
  { "id": 4, "position": 2 }
]
```

> 再採番はサーバーが行うため、**結果の並び順を返します**。画面は先に動かして表示し（楽観的更新）、この結果で正しい状態に合わせます。

| 状況 | コード | 本文の `detail` |
|---|---|---|
| `position` が負 | 400 | 入力内容を確認してください（`errors` に「位置は0以上で指定してください」） |
| `position` がリストの数以上 | 400 | 指定された位置にはリストを置けません |
| 存在しない・他人の・ゴミ箱内のリスト | 404 | リストが見つかりません |

なお **`PUT /api/lists/{listId}`（リスト名の変更）の応答は、ボードの名前変更（4.7）と同じ `{ "id": 5, "name": "やること" }`** です。

### 4.10 POST /api/lists/{listId}/cards（カード作成）

`position` はサーバーが**リストの一番下**に割り当てます。期限日は空、未完了で作られます（要件 8.3）。

```json
// リクエスト
{ "title": "テスト項目表を作る" }
```
```json
// 201 Created   Location: /api/cards/10
{
  "id": 10, "title": "テスト項目表を作る", "description": null,
  "dueDate": null, "isDone": false, "position": 2
}
```

### 4.11 PUT /api/cards/{cardId}（カードの更新）

**4項目すべてを必ず送ります。** 変えたくない項目も、今の値をそのまま送ってください。

```json
// リクエスト（期限日を消し、完了にする例）
{
  "title": "要件定義を書く",
  "description": "01〜01-5 を仕上げる",
  "dueDate": null,
  "isDone": true
}
```
```json
// 200 OK
{
  "id": 8, "title": "要件定義を書く", "description": "01〜01-5 を仕上げる",
  "dueDate": null, "isDone": true, "position": 0
}
```

| 項目 | 必須 | ルール（業務ルール 5.1） |
|---|---|---|
| title | ✕（必須） | 100文字以内。空白だけは不可 |
| description | 任意（null 可） | 2,000文字以内 |
| dueDate | 任意（null 可） | `YYYY-MM-DD`。過去の日付も可。**null は「期限日なし」** |
| isDone | ✕（必須） | true / false |

### 4.12 PATCH /api/cards/{cardId}/move（カードの移動）

```json
// リクエスト（リスト4の、上から3番目へ）
{ "listId": 4, "position": 2 }
```
```json
// 200 OK ＝ 影響したリストの、カードの並び（再採番の結果）
{
  "lists": [
    { "listId": 3, "cardIds": [9, 11] },
    { "listId": 4, "cardIds": [12, 13, 8] }
  ]
}
```

- 同じリスト内の並び替えも、同じエンドポイントで `listId` に今のリストを指定します
- サーバーは1つのトランザクションで「移動元を詰める → 移動先に挿入する → 再採番する」を行います（[03 DB設計書 5.1](03_db-design.md#51-カードを別のリストへ移動するドラッグドロップ)）

| 状況 | コード |
|---|---|
| 移動先リストが他人のもの・存在しない・ゴミ箱内 | 404 |
| `position` が負、またはカード数より大きい | 400 |

### 4.12-2 PUT /api/me/last-opened-board（最後に開いていたボードの記録）

```json
// リクエスト
{ "boardId": 12 }
```

記録するだけなので本文は返さず、**204 No Content** です。

| 状況 | コード |
|---|---|
| 存在しない、または他人のボード | 404 |
| ゴミ箱に入っているボード | 404 |

### 4.13 DELETE /api/boards|lists|cards/{id}（ゴミ箱へ移動）

確認ダイアログは出しません（業務ルール 5.3）。成功すると **204 No Content**（本文なし）です。

- 親をゴミ箱へ移動しても、**子の `deleted_at` は変更しません**（[03 DB設計書 1.1](03_db-design.md#11-ゴミ箱をどう表すか重要)）
- 残ったきょうだいの `position` は詰め直されます
- ボードをゴミ箱へ移動したとき、そのボードが `users.last_opened_board_id` に記録されていれば `null` に戻します。
  記録を残したままだと、次にアプリを開いたときに表示できないボードを取りにいって 404 になるためです（F-15）

### 4.14 GET /api/trash（ゴミ箱一覧）

削除日時の新しい順（業務ルール 5.2）。親がゴミ箱に入っている子は、**親の1件として表示するため含めません**（業務ルール 5.3）。

```json
// 200 OK
[
  {
    "type": "CARD", "id": 8, "name": "要件定義を書く",
    "originalLocation": "学習計画 ＞ TODO",
    "deletedAt": "2026-09-20T03:00:00Z",
    "restorable": true
  },
  {
    "type": "LIST", "id": 4, "name": "DOING",
    "originalLocation": "学習計画",
    "deletedAt": "2026-09-19T10:00:00Z",
    "restorable": true
  },
  {
    "type": "BOARD", "id": 7, "name": "個人タスク",
    "originalLocation": null,
    "deletedAt": "2026-09-18T08:00:00Z",
    "restorable": true
  }
]
```

- `originalLocation` は画面に出す「元の場所」の表示用文字列（F-41）
- `restorable` は「今すぐ元に戻せるか」。親が完全に削除されている場合などは `false` になり、画面は「元に戻す」ボタンを押せないようにします

### 4.15 POST /api/trash/{type}/{id}/restore（元に戻す）

```json
// 200 OK（戻した結果を返す）
{ "type": "CARD", "id": 8, "listId": 3, "position": 4, "message": null }
```

| 状況 | コード | 本文の `detail` |
|---|---|---|
| 元のボードがない（リストを戻すとき） | 409 | 元のボードがないため戻せません |
| 元のリストがないが、同じボードに別のリストがある（カード） | 200 | `message` に「元のリストがないため、一番左のリストに戻しました」 |
| 元のボードにリストが1つもない（カード） | 409 | 戻せる場所がないため戻せません |

> リスト・カードは**末尾**（一番右・一番下）に戻ります（[01-3 業務ルール 5.3](01-3_business-rules.md#元に戻すときのルール)）。

### 4.16 DELETE /api/trash/{type}/{id}（完全に削除）／DELETE /api/trash（空にする）

確認ダイアログは**画面側**で必ず出します（業務ルール 5.3）。API は確認済みとして処理し、**204 No Content** を返します。子のデータは外部キーの `ON DELETE CASCADE` で一緒に削除されます。

## 5. 画面と API の対応

| 画面・操作 | 呼ぶ API |
|---|---|
| アプリを開いたとき | `GET /api/auth/me` → 200 なら `GET /api/boards` と `GET /api/boards/{lastOpenedBoardId}`、`GET /api/trash/count` |
| ログイン画面（S-02） | `POST /api/auth/login` |
| 新規登録画面（S-03） | `POST /api/auth/signup` |
| サイドバーでボードを選ぶ | `GET /api/boards/{id}` ＋ `PUT /api/me/last-opened-board` |
| カードをドラッグ | `PATCH /api/cards/{id}/move` |
| チェックボックスを押す | `PUT /api/cards/{id}`（`isDone` を反転し、他の項目は今の値を送る） |
| ゴミ箱を開く | `GET /api/trash` |

> 通信の失敗はすべて「保存できませんでした」などのメッセージを出し、やり直せるようにします（F-04）。TanStack Query の `onError` で画面を元の状態へ戻します。

## 7. セキュリティ設定の要点（実装時の指針）

```
/api/auth/signup, /api/auth/login  … 未ログインでも許可
それ以外の /api/**                 … 認証必須（未ログインは 401）
CSRF                               … 有効（CookieCsrfTokenRepository）
セッション                           … 既定（メモリ）／タイムアウト 30日
CORS                               … 許可オリジンを限定、allowCredentials = true
パスワード                           … BCryptPasswordEncoder
```

加えて、**すべての Service で「そのデータがログイン中の利用者のものか」を確認**します。URL の ID を書き換えれば他人のデータに届いてしまうため、ここが抜けると要件 6.1 を満たせません。他人のデータのときは 403 ではなく **404** を返します（存在を知らせないため）。

## 8. 検討中・次工程で決めること

| No | 内容 | 現在の案 |
|---|---|---|
| 1 | セッションを DB に保存するか（30日保持の確実化） | バージョン1では見送り（1.1 のとおり要件を修正済み）。「機能追加」フェーズで Spring Session JDBC を検討する |
| 2 | ボード一覧に、リストやカードの件数を含めるか | 含めない案（サイドバーに件数を出す要件はないため） |
| 3 | 移動 API の応答を「並び順のみ」にするか、ボード全体を返すか | 並び順のみ（4.12）。データ量が小さく、楽観的更新と相性が良い |
| 4 | 通信エラー時の自動リトライ | TanStack Query の既定（GET は数回リトライ、更新系はしない）に任せる案 |
