### 1.3 データベースの選択：なぜ RDS にしたか

DB の置き場所には2つの案がありました。**当初は費用を優先して案Aで設計しましたが、案Bに変更しています。**

| | A. EC2 上の PostgreSQL コンテナ | **B. RDS for PostgreSQL（採用）** |
|---|---|---|
| 追加費用 | **$0**（EC2 に同居） | 約 **$21／月** |
| 自動バックアップ | **なし**（自分で `pg_dump` する） | **あり**（特定時点に戻せる） |
| `terraform destroy` したら | **データも消える** | EC2 だけ消してデータを残せる |
| EC2 を作り直したら | **データが消える** | データは残る |
| メモリ | EC2 の 1GB をアプリと奪い合う | DB 専用に 1GB |
| 必要なサブネット | 1つ | **2つ**（AZ をまたぐ必要がある。理由は 7.6） |
| 開発環境との差 | 小さい（`compose.yaml` とほぼ同じ） | やや大きい（接続先が変わる） |

**変更した理由**

1. **データが消える設計は運用が苦しい。** 案Aでは `destroy` のたびに手動バックアップが必要で、
   手順を1つ飛ばすとデータを失います（10.4）
2. **費用が問題にならないと分かった。** 1.4 の試算で、RDS を足しても総額 $27 程度で、
   見込みクレジットの範囲に十分収まります
3. **クレジットが $20 増える。** RDS の作成は付与アクティビティの1つです（1.4）。
   実質の追加負担は月 $1 程度になります
4. **スクール教材の構成と揃う。** 教材の参考資料も RDS を使う構成でした
5. **実務で使うのは RDS 側。** バックアップやサブネットグループなど、現場で必要な知識に触れられます

> **案Aが悪いわけではありません。**
> 「触る時間が短く、データが消えても作り直せる」用途なら、案Aのほうが安く単純です。
> 判断の分かれ目は**データを失って困るかどうか**です。

「ほぼ無料」と言いましたが、**完全に $0 ではありません。** 内訳を正直に書きます。

> **金額は USD で記載します。** AWS の請求も課金の単位も USD であり、
> 円換算は為替レートで変わってしまうためです。日本円で必要になったときは、

>
> AWS の無料利用枠は、**アカウントを作った時期によって内容がまったく違います。**
>
> | 方式 | 対象 | 内容 |
> |---|---|---|
> | 従来型 | 2025年7月より前に作られたアカウント | 作成から**12か月間**、各サービスに一定量の無料枠 |

>
> **このプロジェクトのアカウントは 2026-09-27 に作成したため、新方式に該当します。**
> したがって「12か月間 EC2 が無料」ではなく、**クレジットを消費しながら動かす**形になります。
>
> - 有効期限：**2027-03-27 頃まで**（作成から6か月）
> - クレジットを使い切ると、**そこから先は通常料金が請求されます**
> - 残高は [請求ダッシュボードの「無料利用枠」ページ](https://console.aws.amazon.com/billing/home#/freetier) で確認できます。**手順A（4.4）で必ず確認してください**

#### 実際に使えるクレジットはいくらか

クレジットは2階建てになっています。

| 内訳 | 金額 | 状態 |
|---|---|---|
| 登録時に自動付与 | **$100** | ✅ 付与済み |
| アクティビティ達成による追加 | 最大 $100（$20 × 5種類） | 一部のみ達成予定（下表） |

**「最大 $200」を分母にしてはいけません。** 追加分は、AWS が用意した5つの課題を達成した場合にのみ付与されるためです。
本プロジェクトで実際に達成するのは次の2つだけです。

| アクティビティ | 特典 | 本プロジェクトとの関係 | 判断 |
|---|---|---|---|
| AWS Budgets を使用してコスト予算をセットアップする | $20 | ✅ 手順A（4.3）でやること | **✅ 達成済み** |
| EC2 を使用してインスタンスを起動する | $20 | ✅ 手順D（8章）で必ず起動する | **⬜ 自動的に達成される** |
| オーロラまたは RDS データベースを作成する | $20 | ✅ **本構成で RDS を採用したため、8章の `apply` で達成される** | **⬜ 自動的に達成される** |
| Amazon Bedrock のプレイグラウンドで基盤モデルを使用する | $20 | ❌ 本プロジェクトと無関係 | ⬜ 見送り |
| AWS Lambda を使用してウェブアプリケーションを作成する | $20 | ❌ 本プロジェクトと無関係 | ⬜ 見送り |

**したがって、本プロジェクトで見込めるクレジットは $100 ＋ $20 ＋ $20 ＋ $20 ＝ 約 $160 です。**
以降の判断はこの **$160**（控えめに見るなら $140）を分母にします。

> **⚠️ クレジット目当てで無関係なアクティビティをやらないこと**
> Bedrock と Lambda は本プロジェクトで使わないため実施しません。
> 作ったものを消し忘れると、得られる $20 を上回る請求を招くことがあります。
>
> **RDS は「無関係なのにやる」のではなく、構成として必要だから作ります。**
> この違いは大事です。クレジットは結果として付いてくるものであり、目的ではありません。

## 2. 前提知識の解説（ここを飛ばさない）

### 2.1 AWS とは何か

AWS（Amazon Web Services）は、Amazon が貸し出している**コンピューターとネットワークの部品の集まり**です。

これまで、自分の PC で `docker compose up -d` を実行して PostgreSQL を動かしてきました。
その PC が「インターネットの向こう側にあって、24時間動いていて、誰でもアクセスできる」ようになったもの、と考えると分かりやすいです。

AWS には200以上のサービスがありますが、**今回使うのは次の7つだけ**です。

| サービス | 何をするもの | 身近な例えで言うと |
|---|---|---|
| **IAM** | 誰が何をしてよいかを決める（認証・認可） | 社員証と、入れる部屋の権限 |
| **VPC** | 自分専用のネットワーク空間 | 自分の家のネットワーク（Wi-Fi ルーターの内側） |
| **サブネット** | VPC をさらに区切った小部屋 | 家の中の「リビング」「書斎」 |
| **インターネットゲートウェイ (IGW)** | VPC をインターネットにつなぐ出入口 | 家の玄関・光回線の引き込み口 |
| **セキュリティグループ (SG)** | どの通信を通すかの関所 | 玄関のドアと鍵。「80番ポートの人だけ通す」 |
| **EC2** | 仮想のコンピューター1台 | レンタルした PC |
| **ECR** | Docker イメージの保管庫 | 自分専用の Docker Hub |
| **RDS** | AWS が運用してくれるデータベース | 管理人付きのサーバー室。バックアップや更新を代行してくれる |

#### リージョンとアベイラビリティゾーン

AWS のデータセンターは世界中にあります。

- **リージョン（Region）**：国・地域の単位。東京は `ap-northeast-1`。日本のユーザー向けなら東京を選ぶ
- **アベイラビリティゾーン（AZ）**：リージョン内の、物理的に離れたデータセンター。東京には `ap-northeast-1a`〜`1d` がある。片方が地震や停電で止まっても、もう片方が生き残るように分かれている

今回、アプリを動かす EC2 は **1つの AZ にだけ**置きます（本番なら2つ以上に分散させます）。

ただし **データベース（RDS）だけは、2つの AZ にまたがるサブネットの組を必ず要求されます。**
冗長化しない設定（単一 AZ）で作る場合でも同じです。AWS が後から別の AZ へ移せるように、
置き場所の候補を確保しておく仕組みだからです。
そのため、実際には使わない2つ目のサブネットも作ります（7.6・7.8）。

> **落とし穴**：マネジメントコンソールは「今どのリージョンを見ているか」で表示が変わります。
> 東京で作ったのにバージニア北部（`us-east-1`）を見ていて「リソースが無い！」と慌てるのは、初心者が必ず1回は通る道です。
> 画面右上のリージョン名を常に確認してください。

### 2.2 IaC（Infrastructure as Code）とは何か

**IaC ＝ インフラをコードで書いて管理すること**です。

#### 手で作ると何が困るのか

マネジメントコンソールで EC2 を1台作るには、画面上で20回ほどクリックし、10項目ほど入力します。これ自体は難しくありません。問題はその後です。

| 困ること | 具体的に |
|---|---|
| **再現できない** | 1か月後に同じものをもう1台作れと言われて、全く同じ設定にできますか？ |
| **記録が残らない** | 「このセキュリティグループ、なぜ 3000 番ポートが開いているんだっけ？」誰も分からない |
| **レビューできない** | クリック操作は Pull Request に載せられない。間違いに誰も気づけない |
| **消し忘れる** | 作ったものを全部覚えていますか？ 消し忘れたリソースは課金され続けます |
| **壊れたときに直せない** | 何が正しい状態だったのかが分からない |

#### コードで書くとどうなるか

```hcl
resource "aws_instance" "app" {
  instance_type = "t2.micro"
  ami           = "ami-xxxxxxxx"
}
```

このテキストファイルが「インフラの設計図」そのものになります。すると：

- **Git で管理できる** → 変更履歴が残り、PR でレビューでき、間違えたら戻せる
- **同じものを何度でも作れる** → 開発環境・本番環境を同じコードから作れる
- **1コマンドで全部消せる** → 消し忘れによる課金事故が起きない
- **ドキュメントになる** → コードを読めば構成が分かる。人の記憶に頼らない

これは、みなさんが既にやっていることと同じ発想です。
**Flyway で DB のテーブル定義を SQL ファイルで管理している**のと、**Dockerfile で実行環境を手順書として書いている**のと、まったく同じ考え方を、サーバーやネットワークにまで広げたものが IaC です。

| 対象 | コードで管理する道具 |
|---|---|
| DB のテーブル定義 | Flyway（このプロジェクトで既に使用中） |
| アプリの実行環境 | Dockerfile（このプロジェクトで既に使用中） |
| ビルドとテストの手順 | GitHub Actions（このプロジェクトで既に使用中） |
| **サーバー・ネットワーク** | **Terraform（今回導入するもの）** |

### 2.3 Terraform とは何か

Terraform は HashiCorp 社が作った、**最も広く使われている IaC ツール**です。

#### 仕組み

Terraform は3つの状態を比べて動きます。

```
 ①コード (.tf)          ②状態ファイル              ③実際の AWS
 「こうあってほしい」     (terraform.tfstate)        「今こうなっている」
 EC2 1台、t2.micro       「前回こう作った」と        EC2 1台、t2.micro
                          いう記録
        │                       │                          │
        └───────────────────────┴──────────────────────────┘
                                │
                        差分を計算して
                        「足りないものを作る／
                          余分なものを消す／
                          違うものを直す」
```

この「**あるべき姿を書いておくと、Terraform が現実をそこに合わせてくれる**」考え方を**宣言的（declarative）**と言います。

対義語は**手続き的（imperative）**で、「EC2 を作れ → 次にセキュリティグループを作れ → 次に…」と手順を書く方式です。手続き的だと「もう作ってあるときはどうするの？」を自分で書く必要がありますが、宣言的ならその判断は Terraform がやってくれます。

#### 主なコマンド

| コマンド | 何をするか | 危険度 |
|---|---|---|
| `terraform init` | 必要なプラグイン（AWS 用の部品）をダウンロードする。最初に1回 | 安全 |
| `terraform fmt` | コードを整形する（`./gradlew spotlessApply` と同じ役割） | 安全 |
| `terraform validate` | 文法が正しいか確認する | 安全 |
| `terraform plan` | **「これから何をするか」を表示するだけ。実際には何もしない** | 安全 |
| `terraform apply` | plan の内容を実際に AWS に反映する | **要注意** |
| `terraform destroy` | 作ったものを全部消す | **危険** |

> **鉄則：`apply` の前に必ず `plan` を読む。**
> `plan` の出力には `+`（作成）`-`（削除）`~`（変更）の記号が付きます。
> **`-` や `~` が意図しないところに出ていたら、絶対に apply しないでください。**
> 特に `-/+`（destroy and then create replacement）は、既存のサーバーやデータベースを**作り直す＝データが消える**という意味です。

#### 状態ファイル（tfstate）の重要性

`terraform.tfstate` は Terraform の生命線です。これを失うと、Terraform は「自分が何を作ったか」が分からなくなり、既存のリソースを管理できなくなります。

- **Git にコミットしてはいけない**（DB のパスワードなどが平文で入ることがある）
- 今回は学習用なので手元のファイルとして持ちますが、**チーム開発では S3 に置くのが標準**です（8.6 で解説）

### 2.4 なぜ「AWS CLI」と「Terraform」の両方が要るのか

役割が違います。

| 道具 | 役割 | 例え |
|---|---|---|
| **AWS CLI** | AWS と話すための**認証情報**を持ち、単発の操作や確認をする | 社員証と、窓口で個別に手続きすること |
| **Terraform** | インフラ全体の**構成を管理**する。認証は AWS CLI の設定を借りる | 建築の設計図と施工 |

Terraform は裏側で AWS CLI と同じ認証情報（`~/.aws/credentials`）を読んで動きます。
なので **手順B（AWS CLI の認証設定）が先、手順C（Terraform）が後**という順番になります。

### 2.5 AI（Claude Code）にデプロイをやらせるときの注意

AI にコマンドを実行させるのは効率的ですが、**AWS は実際にお金がかかる**点が、ローカル開発と決定的に違います。次のルールを守ってください。

| ルール | 理由 |
|---|---|
| **`terraform apply` と `terraform destroy` は、必ず自分で内容を読んでから実行する** | AI が生成した plan を読まずに apply するのは、白紙の契約書にサインするのと同じ |
| **`-auto-approve` オプションは使わない** | 確認のワンクッションが消える。事故の温床 |
| **請求アラートを先に設定する**（手順A） | 何かが暴走したときの最後の砦 |
| **アクセスキーを AI に読ませない・貼らない** | 会話ログやコードに残ると流出する。`~/.aws/credentials` に置き、コードからは参照しない |
| **`.gitignore` に `*.tfstate` `*.tfvars` を必ず入れる** | GitHub に公開鍵情報が流出する事故は実際に多い |

このプロジェクトの [CLAUDE.md](../CLAUDE.md) のルール（Issue を立てる → ブランチを切る → PR）は、インフラのコードにも同じように適用してください。**インフラの変更こそレビューが要ります。**

### 2.6 今回使うその他の用語

| 用語 | 意味 |
|---|---|
| **AMI** | Amazon Machine Image。EC2 の OS テンプレート。「Amazon Linux 2023 の入った初期状態のディスク」 |
| **EBS** | EC2 にくっつく仮想ハードディスク |
| **Elastic IP (EIP)** | 固定のグローバル IP アドレス。付けないと EC2 の再起動で IP が変わる |
| **インスタンスプロファイル** | EC2 に持たせる「社員証」。これがあると EC2 は自分の権限で ECR からイメージを取得できる（アクセスキーを EC2 に置かずに済む） |
| **SSM Session Manager** | SSH の鍵なしで EC2 のシェルに入れる仕組み。22番ポートを開けずに済むので安全 |
| **ユーザーデータ (user_data)** | EC2 が初回起動したときに1回だけ実行されるスクリプト |
| **CIDR** | `10.0.0.0/16` のような IP アドレス範囲の書き方。`/16` は「前半16ビットが固定」＝約65,000個のアドレス |

### 2.7 （参考）本番ならどうするか

今回はコスト最優先で「EC2 1台に全部乗せ」ですが、実務では次のようにします。**この差を知っておくことが、課題の説明でも効きます。**

| 観点 | 今回（学習用） | 本番相当 |
|---|---|---|
| アプリの実行 | EC2 1台の Docker | ECS Fargate ＋ ALB（複数台に自動分散、自動復旧） |
| DB | RDS（単一 AZ、自動バックアップあり） | RDS（**複数 AZ 冗長化**、リードレプリカ） |
| DB の場所 | **プライベートサブネット**（採用済み） | 同じ |
| サーバーが落ちたら | 手で再起動 | Auto Scaling が自動で入れ替え |
| DB のデータが消えたら | **特定時点への復元が可能**（保持7日） | 同じ（保持期間を長く取る） |
| 公開範囲 | 自分の IP のみ（学習用のため） | 全世界に公開し、WAF・認証・レート制限で守る |
| HTTPS | Let's Encrypt を手で設定 | ACM（無料の証明書）＋ ALB / CloudFront |
| tfstate の置き場 | 手元のファイル | S3 ＋ ロック |
| 認証 | IAM ユーザーのアクセスキー | IAM Identity Center（一時的な認証情報） |

### 4.1 ルートユーザーと IAM ユーザーの使い分け（確認）

AWS アカウントを作ったときのメールアドレスでログインするユーザーが **ルートユーザー**です。
これは**何でもできてしまう最強の権限**を持ちます。アカウントの解約すらできます。

**ルートユーザーは普段使いしてはいけません。** 乗っ取られたら終わりだからです。
日常の操作は、すでに作成済みの IAM ユーザーで行います。

| ユーザー | 使う場面 |
|---|---|
| ルートユーザー | 請求設定の変更、アカウントの解約、IAM ユーザーでは触れない設定（4.5 など）。**年に数回** |
| IAM ユーザー | それ以外すべて。コンソールへのログインも、CLI からの操作も | 

> **今日からの運用ルール**：コンソールにログインするときは **IAM ユーザーのサインイン URL**
> （`https://＜アカウントID＞.signin.aws.amazon.com/console`）をブックマークし、そこから入る。
> ルートユーザーのログインは封印する。

### 4.2 MFA の確認（設定済み）

MFA（多要素認証）＝ パスワードに加えて、スマホのアプリが出す6桁の数字も要求する仕組みです。
パスワードが漏れても、スマホが無ければ入れません。

**ルートユーザー・IAM ユーザーとも設定済みです。** 念のため表示だけ確認してください。

- ルートユーザー：ルートでログイン → 右上のアカウント名 → 「セキュリティ認証情報」→ 「多要素認証 (MFA)」にデバイスが1つ表示されている
- IAM ユーザー：IAM → ユーザー → 該当ユーザー → 「セキュリティ認証情報」タブ → 「多要素認証 (MFA)」にデバイスが表示されている

> **⚠️ 今のうちにやっておくと安心なこと**
> スマホを機種変更・紛失すると AWS に入れなくなります。**特にルートユーザーは、失うと復旧が非常に面倒です。**
> - 認証アプリのバックアップ機能を有効にしておく（Google Authenticator のクラウド同期など）
> - または、2つ目の MFA デバイスを登録しておく（AWS は1ユーザーに最大8個まで登録できます）
>
> セットアップ時のシークレットキーを保存していない場合は、**2つ目のデバイスを追加する**のが現実的な保険です。

### 4.3 予算アラートを $5 に変更する（この章の主作業）

現在 **$20** で設定済みですが、**$5 に変更**します。

#### なぜ $5 にするのか

1.4 のとおり、**このプロジェクトの想定月額は約 $12（作業時だけ起動する使い方）**です。

| 予算額 | 何を検知できるか |
|---|---|
| $20（現状） | 想定月額の2倍近い。**リソースを消し忘れて常時稼働していても（月 $38）気づくのが月末近くになる。** 一番ありがちな失敗を見逃しやすい |
| **$5（推奨）** | 想定月額を大きく下回る。**「作業していないのに課金されている」＝消し忘れを確実に捉えられる** |

> **$5 は「異常検知」ではなく、次の2つの検知器として効きます。**
> 1. **クレジットが尽きて実課金に切り替わったこと**（1.4 のとおり、尽きた瞬間から通常請求になる）
> 2. **リソースの消し忘れ**（特に EC2 の停止忘れ、Elastic IP の消し忘れ）

#### ⚠️ 設定時の重要な注意：クレジットの扱い

予算を作る／編集する画面の**「詳細オプション」に、クレジットを費用に含めるかの設定**があります。
ここの扱いで、アラートの意味が正反対になります。

| 設定 | 月々の「実績コスト」の見え方 | 結果 |
|---|---|---|
| **クレジットを含める（既定／推奨）** | クレジットが相殺するので **$0 近くで推移し、尽きた月から跳ね上がる** | ✅ 静かなまま、**本当に課金が始まった瞬間だけ鳴る** |
| クレジットを除外する | クレジットに関係なく実使用量（約 $12）が計上される | ❌ **毎月鳴る。** 慣れて無視するようになり、本当の異常を見逃す |

**「クレジットを含める」（チェックが入った状態＝既定）のままにしてください。**
これにより、$5 の予算は「クレジットが尽きるまでは沈黙し、尽きたら鳴るスイッチ」として機能します。

#### 変更手順

1. ルートユーザーまたは IAM ユーザー（4.5 を実施済みなら IAM で可）でコンソールにログイン
2. 右上のアカウント名 → **「請求とコスト管理」**
3. 左メニュー **「Budgets（予算）」**
4. 既存の予算（$20 のもの）を選び、**「編集」**
5. 次のように変更する

| 項目 | 変更後の設定値 |
|---|---|
| 予算名 | `taskboard-monthly`（分かる名前ならそのままでよい） |
| 予算額 | **$20 → 5 USD** |
| アラートのしきい値① | 実績コスト（Actual）の **80%** ＝ $4 で通知 |
| アラートのしきい値② | **予測コスト（Forecasted）の 100%** ＝ 「このペースだと月末に $5 を超える」時点で通知 |
| 通知先メール | 自分のメールアドレス |

6. 保存する

> **しきい値を2つ設定する理由**
> 「実績」だけだと、**すでに使ってしまった後**に通知が来ます。
> 「予測」も入れておくと、**月初のうちに「このペースはまずい」と気づける**ようになります。

#### 追加でやっておくこと

### 5.1 既存の IAM ユーザーの権限を確認する（重要）

Terraform を動かすには、その IAM ユーザーに**十分な権限**が必要です。ここが足りないと 8章で必ず止まります。

1. コンソールの検索窓に `IAM` と入力して IAM のページへ
2. 左メニュー **「ユーザー」** → 既存のユーザーを選択
3. **「許可」タブ**を開き、付与されているポリシーを確認する

**`AdministratorAccess` が付いていれば、そのまま先へ進めます。**

付いていない場合は追加します。

1. 「許可」タブ → 「許可を追加」→ **「ポリシーを直接アタッチする」**
2. `AdministratorAccess` を検索してチェック → 「許可を追加」

> **なぜ AdministratorAccess なのか**
> 本来は「必要最小限の権限だけ与える」のが原則（最小権限の原則）です。
> しかし Terraform は VPC・EC2・IAM・ECR など多方面のリソースを作るため、
> 学習段階で権限を絞ると「権限エラーで止まる → 調べる → 足す」の繰り返しで前に進めません。
> **学習用と割り切って Administrator にし、代わりに MFA と予算アラートで守ります。**
> 実務では、Terraform 専用の絞ったロールを使います。
>
> なお、9.5 で作る GitHub Actions 用のロールは**最小権限（ECR への push のみ）**にしてあります。
> 「人が使うユーザーは広く、自動化に渡す権限は狭く」という使い分けを意識してください。


対話形式で4つ聞かれます。


#### 続けて聞かれる2つの質問（どちらも `n` を選ぶ）

AWS CLI 2.37 以降では、上の4項目のあとに **AWS Agent Toolkit** に関する質問が続きます。
**本プロジェクトではどちらも不要なので、`n` を入力してください。**

```

Configure AWS MCP server connection? [Y/n]: → n
```

> **⚠️ 既定値が「はい」になっています。**
> `[Y/n]` は**大文字の `Y` が既定**という意味です。**何も入力せず Enter を押すと「はい」が選ばれます。**
> 見送るときは、必ず `n` を明示的に入力してください。

| 質問 | 何を設定するものか | 判断 | 理由 |
|---|---|---|---|
| AWS skills | AI コーディングエージェント（Claude Code など）に、AWS 各サービスの指示書を配る仕組み | **`n`** | カタログに **Terraform 用のスキルが存在しない**（CDK・CloudFormation 用はあるが今回は使わない） |
| AWS MCP サーバー | AI エージェントから AWS の情報を直接引けるようにする接続設定 | **`n`** | AI は **AWS CLI をそのまま実行できる**ため、できることがほとんど増えない。認証情報を渡す経路を増やさない（2.5 の方針） |

**どちらも後からいつでも追加できます。** 見送ったことによる不利益はありません。

誤って `Y` を選んでしまった場合は、次のコマンドで確認・削除できます。

```powershell
# 入っているスキルの一覧（何も入っていなければ空で返る）
aws agent-toolkit list-installed-skills --region us-east-1

# 削除する
aws agent-toolkit remove-skill --skill-name <名前> --region us-east-1
```

> `agent-toolkit` の各コマンドは **us-east-1 でしか動きません**。
> 既定のリージョン（ap-northeast-1）のままだと `AgentToolkit is only available in us-east-1` というエラーになるため、
> `--region us-east-1` を明示してください。

### 6.3 Terraform のコードの書き方（HCL）

Terraform のコードは **HCL（HashiCorp Configuration Language）** という言語で書きます。
JSON に似ていますが、コメントが書けて読みやすくなっています。

出てくる部品は5種類だけです。

```hcl
# ① terraform ブロック：Terraform 自体の設定（どのプラグインを使うか）
terraform {
  required_providers {
    aws = { source = "hashicorp/aws", version = "~> 6.0" }
  }
}

# ② provider ブロック：接続先の設定（どのクラウドの、どのリージョンか）
provider "aws" {
  region = "ap-northeast-1"
}

# ③ variable ブロック：外から渡す設定値（Java のメソッド引数のようなもの）
variable "project_name" {
  type    = string
  default = "taskboard"
}

# ④ resource ブロック：実際に作るもの（これが本体）
#    resource "＜種類＞" "＜このコード内での呼び名＞" { 設定 }
resource "aws_vpc" "main" {
  cidr_block = "10.0.0.0/16"
}

# ⑤ output ブロック：作った後に知りたい値を表示する（戻り値のようなもの）
output "vpc_id" {
  value = aws_vpc.main.id
}
```

**参照の書き方が重要です。**
`aws_vpc.main.id` は「`aws_vpc` 型の `main` という名前のリソースの `id` 属性」という意味です。
この参照を書くと、Terraform は「VPC を作ってからサブネットを作る」という**順番を自動で判断**します。
順番を自分で書く必要はありません。これが宣言的ということです。

## 7. 手順D-1：Terraform のコードを書く

> **この章のゴール**

### 7.1 作業を始める前に（プロジェクトのルール）

[CLAUDE.md](../CLAUDE.md) のルールどおり、まず Issue を立ててブランチを切ります。

```powershell
# main を最新にする

git pull

# ブランチを切る（Issue 番号は実際のものに置き換える）

```

Issue のタイトル例：「AWS へのデプロイ基盤を Terraform で構築する」
ラベル：`infra`

### 7.2 フォルダを作る

```powershell
mkdir infra\terraform
```

最終的に次のファイル構成になります。

```
infra/terraform/
├── versions.tf              … Terraform とプロバイダのバージョン指定
├── variables.tf             … 外から渡す設定値の定義
├── network.tf               … VPC・サブネット（パブリック/プライベート）・ルーティング・SG
├── iam.tf                   … EC2 に持たせる権限
├── ecr.tf                   … コンテナイメージの置き場
├── rds.tf                   … データベース（RDS）とサブネットグループ・DB 用 SG
├── ec2.tf                   … サーバー本体
├── github_oidc.tf           … GitHub Actions に ECR への push を許可する設定（9.5 で解説）
├── outputs.tf               … 作成後に表示したい値
├── user_data.sh             … EC2 の初回起動時に走るスクリプト
├── .terraform.lock.hcl      … プロバイダの版数を記録したファイル（Git に入れる）
├── terraform.tfvars         … 設定値の実際の中身（**Git に入れない**）
└── terraform.tfvars.example … 上のひな形（Git に入れる）
```

> **本書に載せているコードは解説用です。**
> 実際に動いているのは `infra/terraform/` の各ファイルです。
> 食い違いを見つけたら、**リポジトリのコードが正**として本書を直してください（[CLAUDE.md](../CLAUDE.md) 2章の方針）。

> **なぜファイルを分けるのか**
> Terraform は `.tf` ファイルを**全部まとめて1つとして読みます**。分ける必要は技術的にはありません。
> しかし1ファイルに300行書くと読めなくなるので、**役割ごとに分けるのが慣習**です。
> Java でクラスを分けるのと同じ理由です。

### 7.3 `.gitignore` を先に書く（これを最初にやる）

**コードを書く前にこれを設定してください。** 順番を逆にすると事故ります。

リポジトリ直下の `.gitignore` に次を追記します。

```gitignore
# Terraform
**/.terraform/*
*.tfstate
*.tfstate.*
*.tfvars
!*.tfvars.example
.terraform.lock.hcl.bak
crash.log
```

| 除外するもの | 理由 |
|---|---|
| `.terraform/` | ダウンロードしたプラグイン。数百MBになる。`init` で再取得できる |
| `*.tfstate` | **DB パスワードなどが平文で入る。** 最重要 |
| `*.tfvars` | 設定値。パスワードを書くことがある |

### 7.4 `versions.tf`

```hcl
# Terraform 本体と、使用するプロバイダ（AWS 用の部品）のバージョンを固定する。
# バージョンを固定する理由：
#   プロバイダが勝手に新しくなると、同じコードでも挙動が変わることがある。
#   build.gradle.kts で依存ライブラリのバージョンを書くのと同じ考え方。

terraform {
  # 1.9 以上であれば動く、という意味
  required_version = ">= 1.9"

  required_providers {
    aws = {
      source = "hashicorp/aws"
      # "~> 6.0" は「6.x系なら上げてよいが 7.0 にはしない」という意味
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = var.aws_region

  # すべてのリソースに自動で付けるタグ。
  # タグを付けておくと「どのプロジェクトのリソースか」が請求画面で分かり、消し忘れにも気づける
  default_tags {
    tags = {
      Project   = var.project_name
      ManagedBy = "Terraform"
    }
  }
}
```

### 7.5 `variables.tf`

```hcl
# 外から渡す設定値の定義。
# ここには「型」と「説明」と「既定値」だけを書き、実際の値は terraform.tfvars に書く。

variable "project_name" {
  description = "リソース名の先頭に付ける、このプロジェクトの識別子"
  type        = string
  default     = "taskboard"
}

variable "aws_region" {
  description = "リソースを作るリージョン"
  type        = string
  default     = "ap-northeast-1"
}

variable "vpc_cidr" {
  description = "VPC のアドレス範囲。他のネットワークと重ならなければ何でもよい"
  type        = string
  default     = "10.0.0.0/16"
}

variable "public_subnet_cidr" {
  description = "パブリックサブネットのアドレス範囲。VPC の範囲に収まっている必要がある"
  type        = string
  default     = "10.0.1.0/24"
}

variable "instance_type" {
  description = <<-EOT
    EC2 のサイズ。無料利用枠の対象は、東京リージョンでは t2.micro。
    メモリが 1GB しかないため、user_data.sh でスワップ領域を 2GB 追加している。
  EOT
  type        = string
  default     = "t2.micro"
}

variable "root_volume_size" {
  description = "EC2 のディスクサイズ（GB）。gp3 は $0.096/GB・月"
  type        = number
  default     = 20
}

variable "db_password" {
  description = "PostgreSQL の taskboard ユーザーのパスワード"
  type        = string

  # sensitive = true にすると、plan / apply の出力でこの値が伏せ字になる。
  # ログやスクリーンショットからの漏洩を防ぐため、秘密の値には必ず付ける
  sensitive = true

  # validation を書いておくと、短すぎるパスワードを plan の時点ではじける。
  # Bean Validation で入力チェックを書くのと同じ発想
  validation {
    condition     = length(var.db_password) >= 16
    error_message = "db_password は16文字以上にしてください。"
  }
}

variable "allowed_app_cidr" {
  description = <<-EOT
    アプリ（80番・443番）へのアクセスを許可する送信元のリスト。
    課題の指示により、インターネット全体には公開せず、作業する PC からだけ届くようにする。

    既定は空リスト。空のままだと 80番・443番は誰にも開かない（安全側に倒している）。
    値は terraform.tfvars に書く。tfvars は .gitignore で除外されているため、
    自分のグローバル IP アドレスが GitHub に載ることはない。
  EOT
  type        = list(string)
  default     = []
}

variable "allowed_ssh_cidr" {
  description = <<-EOT
    SSH（22番ポート）を許可する送信元。
    既定は 0.0.0.0/0（全世界）ではなく空リスト＝誰にも開けない。
    EC2 への接続は SSM Session Manager を使うため、22番を開ける必要がない。
  EOT
  type        = list(string)
  default     = []
```

### 7.6 `network.tf`

```hcl
# ネットワークの箱を作る。
# 「家を建てる」で言えば、土地を用意し、道路につなげ、玄関に鍵を付ける工程にあたる。

# ---------- VPC（自分専用のネットワーク空間） ----------
resource "aws_vpc" "main" {
  cidr_block = var.vpc_cidr

  # VPC 内のリソースに DNS 名（ec2-xx-xx.compute.amazonaws.com のような名前）を割り当てる。
  # ECR からイメージを取得するときに名前解決が必要になるため、両方 true にする
  enable_dns_support   = true
  enable_dns_hostnames = true

  tags = {
    Name = "${var.project_name}-vpc"
  }
}

# ---------- インターネットゲートウェイ（インターネットへの出入口） ----------
# これを VPC に付けないと、中のサーバーは外と通信できない。料金はかからない
resource "aws_internet_gateway" "main" {
  vpc_id = aws_vpc.main.id

  tags = {
    Name = "${var.project_name}-igw"
  }
}

# ---------- アベイラビリティゾーンの一覧を取得する ----------
# data ブロックは「作る」のではなく「AWS から情報を読む」ためのもの。
# AZ の名前をコードに直接書かずに済ませ、他のリージョンでも動くようにしている
data "aws_availability_zones" "available" {
  state = "available"
}

# ---------- パブリックサブネット ----------
# 「パブリック」とは、インターネットゲートウェイへの経路を持つサブネットのこと。
# サブネット自体に public/private という設定項目があるわけではなく、
# ルートテーブルの中身で決まる（初学者が必ず混乱するところ）
resource "aws_subnet" "public" {
  vpc_id            = aws_vpc.main.id
  cidr_block        = var.public_subnet_cidr
  availability_zone = data.aws_availability_zones.available.names[0]

  # このサブネットで起動したインスタンスに、自動でパブリック IP を割り当てる
  map_public_ip_on_launch = true

  tags = {
    Name = "${var.project_name}-public-subnet"
  }
}

# ---------- ルートテーブル（通信の行き先表） ----------
resource "aws_route_table" "public" {
  vpc_id = aws_vpc.main.id

  route {
    # 「VPC 内宛て以外のすべての通信（0.0.0.0/0）は、インターネットゲートウェイへ送る」
    cidr_block = "0.0.0.0/0"
    gateway_id = aws_internet_gateway.main.id
  }

  tags = {
    Name = "${var.project_name}-public-rt"
  }
}

# ルートテーブルをサブネットに結びつける。これで初めて「パブリックサブネット」になる
resource "aws_route_table_association" "public" {
  subnet_id      = aws_subnet.public.id
  route_table_id = aws_route_table.public.id
}

# ---------- セキュリティグループ（サーバーの前に立つ関所） ----------
# セキュリティグループは「許可リスト方式」。書いたものだけが通り、書かないものは全部拒否される。
# また「ステートフル」なので、入りを許可すれば、その応答の戻りは自動的に許可される
# （戻り用のルールを書く必要はない）
resource "aws_security_group" "app" {
  name        = "${var.project_name}-app-sg"
  description = "アプリケーションサーバー用。HTTP/HTTPS のみ受け付ける"
  vpc_id      = aws_vpc.main.id

  tags = {
    Name = "${var.project_name}-app-sg"
  }
}

# インバウンド（入ってくる通信）：HTTP
#
# 0.0.0.0/0（全世界）ではなく、var.allowed_app_cidr に書いた送信元だけに許可する。
# for_each に空のリストを渡すとルールが1つも作られないため、
# allowed_app_cidr を設定しない限り 80番は誰にも開かない
resource "aws_vpc_security_group_ingress_rule" "http" {
  for_each = toset(var.allowed_app_cidr)

  security_group_id = aws_security_group.app.id
  description       = "許可した送信元からの HTTP"
  cidr_ipv4         = each.value
  from_port         = 80
  to_port           = 80
  ip_protocol       = "tcp"
}

# インバウンド：HTTPS（許可する送信元は HTTP と同じ）
resource "aws_vpc_security_group_ingress_rule" "https" {
  for_each = toset(var.allowed_app_cidr)

  security_group_id = aws_security_group.app.id
  description       = "許可した送信元からの HTTPS"
  cidr_ipv4         = each.value
  from_port         = 443
  to_port           = 443
  ip_protocol       = "tcp"
}

# インバウンド：SSH（既定では var.allowed_ssh_cidr が空なので、1つも作られない）
# for_each に空リストを渡すと、このリソースは作られない。これが Terraform での条件分岐の書き方
resource "aws_vpc_security_group_ingress_rule" "ssh" {
  for_each = toset(var.allowed_ssh_cidr)

  security_group_id = aws_security_group.app.id
  description       = "SSH（自分の IP からのみ）"
  cidr_ipv4         = each.value
  from_port         = 22
  to_port           = 22
  ip_protocol       = "tcp"
}

# アウトバウンド（出ていく通信）：すべて許可
# ECR からのイメージ取得、OS のパッケージ更新に必要
resource "aws_vpc_security_group_egress_rule" "all" {
  security_group_id = aws_security_group.app.id
  description       = "すべての送信を許可"
  cidr_ipv4         = "0.0.0.0/0"
  ip_protocol       = "-1" # -1 は「すべてのプロトコル」
}
```

> **注意：PostgreSQL の 5432 番ポートは開けていません。**
> DB は同じ EC2 の中のコンテナとして動き、アプリからは Docker のネットワーク経由で届くため、
> 外部に公開する必要がありません。**DB のポートをインターネットに開けるのは重大な脆弱性です。**

### 7.7 `iam.tf`

```hcl
# EC2 に持たせる「社員証」を作る。
#
# なぜ必要か：
#   EC2 は ECR からイメージを取得する必要がある。そのためには AWS の認証が要る。
#   しかし EC2 の中にアクセスキーを置くのは危険（サーバーが乗っ取られたら鍵ごと盗まれる）。
#   代わりに「ロール」を EC2 に付けると、AWS が自動で短時間だけ有効な認証情報を渡してくれる。
#   これが IAM ロールを使う理由。

# ---------- 信頼ポリシー：このロールを誰が使えるか ----------
data "aws_iam_policy_document" "ec2_assume_role" {
  statement {
    actions = ["sts:AssumeRole"]
    principals {
      type        = "Service"
      identifiers = ["ec2.amazonaws.com"] # EC2 サービスだけがこのロールになれる
    }
  }
}

resource "aws_iam_role" "ec2" {
  name               = "${var.project_name}-ec2-role"
  assume_role_policy = data.aws_iam_policy_document.ec2_assume_role.json
}

# ---------- ECR からイメージを読む権限（AWS が用意済みのポリシーを使う） ----------
resource "aws_iam_role_policy_attachment" "ecr_read" {
  role       = aws_iam_role.ec2.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonEC2ContainerRegistryReadOnly"
}

# ---------- SSM Session Manager で接続するための権限 ----------
# これがあると、SSH 鍵も 22番ポートも無しで EC2 のシェルに入れる。
# 鍵の管理が不要になり、踏み台サーバーも要らない。現在の標準的なやり方
resource "aws_iam_role_policy_attachment" "ssm" {
  role       = aws_iam_role.ec2.name
  policy_arn = "arn:aws:iam::aws:policy/AmazonSSMManagedInstanceCore"
}

# ---------- インスタンスプロファイル ----------
# IAM ロールを EC2 に取り付けるための「ホルダー」。EC2 に限り、この一段が必要になる
resource "aws_iam_instance_profile" "ec2" {
  name = "${var.project_name}-ec2-profile"
  role = aws_iam_role.ec2.name
}
```

### 7.8 `rds.tf`（データベース）

実際のコードは [`infra/terraform/rds.tf`](../infra/terraform/rds.tf) を見てください。
ここでは**設計の勘どころ**だけ説明します。

#### ① なぜサブネットが2つ要るのか

```hcl
resource "aws_db_subnet_group" "main" {
  name       = "${var.project_name}-db-subnet-group"
  subnet_ids = [for s in aws_subnet.private : s.id]  # ← 2つ渡している
}
```

**RDS は「2つ以上の AZ にまたがるサブネットの組」を必ず要求します。**
`multi_az = false`（冗長化しない）で作る場合でも同じです。
AWS が後から別の AZ へ移せるように、置き場所の候補を確保しておく仕組みだからです。

そのため `network.tf` で `aws_subnet.private` を2つ作っています。
**片方（AZ-c）には実際には何も置かれません**が、無いと RDS を作成できません。
「使われないサブネット」を見て無駄だと思わないでください。**RDS の前提条件です。**

#### ② 許可を IP ではなくセキュリティグループで書く

```hcl
resource "aws_vpc_security_group_ingress_rule" "db_from_app" {
  security_group_id            = aws_security_group.db.id
  referenced_security_group_id = aws_security_group.app.id  # ← IP ではない
  from_port                    = 5432
  to_port                      = 5432
  ip_protocol                  = "tcp"
}
```

送信元に **IP アドレスではなくセキュリティグループを指定**しています。
これにより「アプリの役割を持つものだけが DB に触れる」という許可になります。
EC2 を作り直して IP が変わっても、このルールを直す必要はありません。

#### ③ インターネットから隔離する

| 設定 | 効果 |
|---|---|
| プライベートサブネットに配置 | サブネットに `0.0.0.0/0` の経路が無いため、インターネットから到達できない |
| `publicly_accessible = false` | RDS にパブリックな名前・IP を割り当てない |
| DB 用 SG にアウトバウンドを1つも書かない | RDS から外へ出る通信も許可しない |

3つが重なっているのは**多層防御**です。1つ設定を間違えても、残りが効きます。

その代わり、**手元の PC から直接 DB に接続することはできません。**
DBeaver などでつなぎたい場合は EC2 を踏み台にする必要があります（10.2）。

#### ④ バックアップと削除の設定

| 設定 | 値 | 意味 |
|---|---|---|
| `backup_retention_period` | `7` | 7日分の自動バックアップ。**ストレージと同量（20GB）まで無料** |
| `backup_window` | `18:00-19:00` | UTC 表記。**日本時間の 03:00〜04:00** |
| `skip_final_snapshot` | `true` | `destroy` 時に最終スナップショットを取らない。**学習用のため。本番では必ず `false`** |
| `deletion_protection` | `false` | `destroy` でデータベースを消せる。**本番では `true`** |

後半2つは**学習用に「消しやすさ」を優先した設定**です。
大事なデータを入れるようになったら、`terraform.tfvars` で切り替えてください。

```hcl
db_skip_final_snapshot = false
db_deletion_protection = true
```

### 7.9 `ecr.tf`

```hcl
# コンテナイメージの保管庫。自分専用の Docker Hub と考えればよい。
# GitHub Actions がここに push し、EC2 がここから pull する。

resource "aws_ecr_repository" "backend" {
  name = "${var.project_name}-backend"

  # push 時に脆弱性スキャンを自動実行する（無料）
  image_scanning_configuration {
    scan_on_push = true
  }

  # 同じタグで上書き push できるようにする（学習用のため）。
  # 本番では IMMUTABLE にして「一度作ったイメージは書き換えられない」ようにする
  image_tag_mutability = "MUTABLE"

  # terraform destroy のとき、中にイメージが残っていても削除できるようにする。
  # これが false だと「リポジトリが空でない」というエラーで destroy が止まる
  force_delete = true
}

# ---------- ライフサイクルポリシー ----------
# 古いイメージを自動で消す。
# ECR は保管している量に応じて課金される（$0.10／GB・月）。
# Spring Boot のイメージは1つ約 300MB あるため、push のたびに溜めると保管量が膨らむ。
# 学習用途では最新の数件だけあれば十分なので、自動で削除させる
resource "aws_ecr_lifecycle_policy" "backend" {
  repository = aws_ecr_repository.backend.name

  policy = jsonencode({
    rules = [
      {
        rulePriority = 1
        description  = "最新3件だけ残し、それより古いものは削除する"
        selection = {
          tagStatus   = "any"
          countType   = "imageCountMoreThan"
          countNumber = 3
        }
        action = { type = "expire" }
      }
    ]
  })
}
```

### 7.10 `user_data.sh`

EC2 が**初回起動したときに1回だけ** root 権限で実行されるスクリプトです。
「買ってきた PC の初期セットアップ」にあたります。

```bash
#!/bin/bash
# EC2 の初回起動時に1回だけ root 権限で実行される初期設定スクリプト。
# 「買ってきた PC の初期セットアップ」にあたる。
# 実行ログは EC2 内の /var/log/cloud-init-output.log に残る。うまく動かないときはここを見る。
#
# 注意：このファイルは Terraform の templatefile() で読み込まれてから EC2 に渡される。
# そのため、ドル記号と波かっこの書き方に2通りの意味がある。
#   ドル1つ  … Terraform が値を埋め込む（例: db_password, aws_region）
#   ドル2つ  … ドルが1つに減って出力され、Docker Compose やシェルが解釈する
# この違いは、コメント行の中であっても同じように働く（コメントだから安全、ではない）。

set -euxo pipefail

# ---------- 1. スワップ領域を作る ----------
# t2.micro はメモリが 1GB しかない。
# データベースは RDS に分けたが、JVM とビルドツールだけでも足りなくなることがあり、
# メモリ不足になると OOM Killer にプロセスを殺される。
# ディスクの一部をメモリの代わりに使うスワップを 2GB 用意して余裕を持たせる
if [ ! -f /swapfile ]; then
  dd if=/dev/zero of=/swapfile bs=1M count=2048
  chmod 600 /swapfile
  mkswap /swapfile
  swapon /swapfile
  echo '/swapfile none swap sw 0 0' >> /etc/fstab
fi

# ---------- 2. Docker を入れて起動する ----------
dnf update -y
dnf install -y docker
systemctl enable --now docker

# ec2-user が sudo なしで docker を使えるようにする
usermod -aG docker ec2-user

# ---------- 3. Docker Compose プラグインを入れる ----------
# Amazon Linux 2023 のリポジトリには compose プラグインが無いため、手動で配置する
mkdir -p /usr/local/lib/docker/cli-plugins
curl -sSL "https://github.com/docker/compose/releases/latest/download/docker-compose-linux-x86_64" \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
chmod +x /usr/local/lib/docker/cli-plugins/docker-compose

# ---------- 4. アプリの置き場と設定ファイルを作る ----------
mkdir -p /opt/taskboard

# 環境変数ファイル。compose.yaml から読まれる。
# 600 にして、root 以外からは読めないようにする
cat > /opt/taskboard/.env <<ENVFILE
DB_HOST=${db_host}
DB_PORT=${db_port}
DB_NAME=${db_name}
DB_USER=${db_user}
DB_PASSWORD=${db_password}
ECR_IMAGE=${ecr_image}
ENVFILE
chmod 600 /opt/taskboard/.env

# 本番用の compose.yaml
# データベースは RDS に分けたため、ここで動かすのはアプリだけ
cat > /opt/taskboard/compose.yaml <<'COMPOSEFILE'
services:
  app:
    image: $${ECR_IMAGE}
    restart: always
    environment:
      # 接続先は RDS のエンドポイント。値は .env から読まれる
      SPRING_DATASOURCE_URL: jdbc:postgresql://$${DB_HOST}:$${DB_PORT}/$${DB_NAME}
      SPRING_DATASOURCE_USERNAME: $${DB_USER}
      SPRING_DATASOURCE_PASSWORD: $${DB_PASSWORD}
      PORT: 8080
      TZ: Asia/Tokyo
      # メモリ 1GB に収めるための JVM 設定。
      # データベースが同居しなくなったぶん、割り当てを 70% まで広げている
      JAVA_TOOL_OPTIONS: "-XX:MaxRAMPercentage=70 -XX:+UseSerialGC"
    ports:
      # ホストの 80番を、コンテナの 8080番につなぐ。
      # これでブラウザから http://<IP> で届くようになる
      - "80:8080"
COMPOSEFILE

# ---------- 5. ECR にログインしてアプリを起動する ----------
# インスタンスプロファイル（iam.tf）の権限を使うので、アクセスキーは不要。
# 初回はまだイメージが push されていないことがあるため、失敗しても処理を止めない
aws ecr get-login-password --region ${aws_region} \
  | docker login --username AWS --password-stdin ${ecr_registry} || true

cd /opt/taskboard
docker compose pull || true
docker compose up -d || true

# ---------- 6. 再起動時に自動で立ち上がるようにする ----------
cat > /etc/systemd/system/taskboard.service <<'SERVICEFILE'
[Unit]
Description=Taskboard application
Requires=docker.service
After=docker.service

[Service]
Type=oneshot
RemainAfterExit=yes
WorkingDirectory=/opt/taskboard
ExecStart=/usr/bin/docker compose up -d
ExecStop=/usr/bin/docker compose down

[Install]
WantedBy=multi-user.target
SERVICEFILE

systemctl daemon-reload
systemctl enable taskboard.service
```

> **ドル記号の数で意味が変わります（重要）**
> このファイルは Terraform の `templatefile()` 関数で読み込まれ、**ドル1つ＋波かっこの部分が Terraform の値に置換されます。**
>
> | 書き方 | 誰が解釈するか | 例 |
> |---|---|---|
> | ドル1つ | **Terraform**（EC2 に渡す前に値を埋め込む） | `db_host`・`db_password` |
> | ドル2つ | ドルが1つに減って出力され、**Docker Compose** が `.env` を見て解釈する | `DB_HOST`・`ECR_IMAGE` |
>
> ここを間違えると「変数が見つからない」というエラーになります。初見で必ず引っかかる箇所です。
> **コメント行の中でも同じように解釈される**ため、説明文にうっかり書くと `terraform validate` が失敗します。

### 7.11 `ec2.tf`

```hcl
# サーバー本体。

# ---------- AMI（OS イメージ）を取得する ----------
# AMI の ID はリージョンごとに違い、更新もされる。
# ID を直接書かず、AWS が公開しているパラメータから「最新の Amazon Linux 2023」を引いてくる。
# こうしておくと、コードを書き換えずに常に最新の OS を使える
data "aws_ssm_parameter" "al2023_ami" {
  name = "/aws/service/ami-amazon-linux-latest/al2023-ami-kernel-default-x86_64"
}

resource "aws_instance" "app" {
  ami                    = data.aws_ssm_parameter.al2023_ami.value
  instance_type          = var.instance_type
  subnet_id              = aws_subnet.public.id
  vpc_security_group_ids = [aws_security_group.app.id]
  iam_instance_profile   = aws_iam_instance_profile.ec2.name

  # 初回起動時に実行するスクリプト。user_data.sh のテンプレートに値を埋め込む
  user_data = templatefile("${path.module}/user_data.sh", {
    db_password  = var.db_password
    aws_region   = var.aws_region
    ecr_registry = split("/", aws_ecr_repository.backend.repository_url)[0]
    ecr_image    = "${aws_ecr_repository.backend.repository_url}:latest"
  })

  # user_data を変更したらインスタンスを作り直す。
  # user_data は初回起動時にしか走らないため、これが無いと変更が反映されない
  user_data_replace_on_change = true

  root_block_device {
    volume_size = var.root_volume_size # 既定 20GB。$0.096／GB・月 なので約 $1.92／月
    volume_type = "gp3" # 最新世代。gp2 より安く速い
    encrypted   = true  # ディスクを暗号化する。無料。付けない理由がない
  }

  # インスタンスメタデータへのアクセスを IMDSv2 に限定する。
  # 古い IMDSv1 は、アプリの脆弱性（SSRF）経由で認証情報を盗まれる経路になりうる
  metadata_options {
    http_tokens   = "required"
    http_endpoint = "enabled"
  }

  tags = {
    Name = "${var.project_name}-app"
  }
}

# ---------- Elastic IP（固定のグローバル IP） ----------
# これが無いと、EC2 を停止・起動するたびに IP アドレスが変わってしまう
resource "aws_eip" "app" {
  instance = aws_instance.app.id
  domain   = "vpc"

  tags = {
    Name = "${var.project_name}-eip"
  }

  # インターネットゲートウェイが出来上がってから作る
  depends_on = [aws_internet_gateway.main]
}
```

> **⚠️ Elastic IP の課金に注意**
> Elastic IP は「**確保しているだけで課金**」されます（$0.005／時 ＝ 約 $3.65／月）。

> 11章の `terraform destroy` で必ず一緒に消してください。

### 7.14 アクセス元の IP アドレスを設定する

このプロジェクトでは、アプリを**インターネット全体には公開しません**。
作業する PC からだけ届くように、セキュリティグループで送信元を絞ります（7.6）。

#### なぜ絞るのか

**課題でそのように指示されているため**です。あわせて、不特定多数に見せる必要もありません。
公開範囲を狭めることには、はっきりした効果があります。

| 公開範囲 | 何が起きるか |
|---|---|
| `0.0.0.0/0`（全世界） | 公開した直後から、世界中の探索ツールにポートを見つけられる。ログイン画面への総当たり攻撃や、既知の脆弱性を突く通信が日常的に届く |
| **自分の IP のみ（`/32`）** | **そもそも接続が確立しない。** アプリに脆弱性があっても、外から到達できなければ悪用されない |

これは**多層防御**という考え方です。アプリ側の対策（Spring Security・パスワードのハッシュ化）に加え、
**ネットワークの入口でも止める**ことで、片方が破られてももう片方が残ります。

#### 自分のグローバル IP を調べる

「グローバル IP」は、インターネット側から見た自分の回線のアドレスです。
PC の設定画面に出る `192.168.x.x` はルーターの内側のアドレスなので、**これではありません。**

PowerShell で調べます。

```powershell
(Invoke-RestMethod https://checkip.amazonaws.com).Trim()
```

`203.0.113.10` のような4つの数字が返ります。

#### terraform.tfvars に書く

```hcl
# 末尾の /32 は「このアドレス1つだけ」という意味
allowed_app_cidr = ["203.0.113.10/32"]
```

> **`/32` を忘れないでください。** CIDR 表記では、`/32` が「1アドレスだけ」、
> `/24` なら「256アドレス分」、`/0` なら「全世界」を意味します。
> 書き忘れると AWS 側でエラーになるため、`variables.tf` の `validation` で先に気づけるようにしてあります。

**この値は `terraform.tfvars` に書くので、GitHub には載りません**（7.3 で除外済み）。
自宅の IP アドレスを公開リポジトリに晒さずに済みます。

#### ⚠️ IP が変わるとつながらなくなる

家庭用の回線では、**グローバル IP はときどき変わります**（ルーターの再起動、回線の再接続、ISP の都合など）。
また、次のような場合も届きません。

| 場面 | 結果 |
|---|---|
| ルーターを再起動して IP が変わった | ❌ つながらない |
| スマホのテザリングで接続した | ❌ つながらない（別の回線＝別の IP） |
| 学校や外出先の Wi-Fi から見た | ❌ つながらない |
| スマホの回線から見た | ❌ つながらない |

**これは故障ではなく、設定どおりの動作です。** つながらなくなったら、次の手順で復旧します。

```powershell
# 1. 今の IP を調べ直す
(Invoke-RestMethod https://checkip.amazonaws.com).Trim()

# 2. terraform.tfvars の allowed_app_cidr を書き換える

# 3. 反映する（セキュリティグループのルールだけが入れ替わる。EC2 は作り直されない）
terraform -chdir=infra/terraform plan
terraform -chdir=infra/terraform apply
```

`plan` は `1 to add, 0 to change, 1 to destroy`（古いルールを消して新しいルールを作る）になります。
**EC2 やデータベースには影響しません。**

> **複数の場所から使いたい場合**は、リストに追加できます。
> ```hcl
> allowed_app_cidr = ["203.0.113.10/32", "198.51.100.20/32"]
> ```
> ただし**学校や公衆 Wi-Fi の IP を書くと、その回線を使う全員に開く**ことになります。注意してください。
>
> **デモで他の人に見せる必要が出たとき**は、一時的に `["0.0.0.0/0"]` にして apply し、
> 終わったら元に戻して apply し直す、という運用ができます。
> これも「設定をコードで管理している」利点の1つです。

## 8. 手順D-2：インフラを作る

> **この章のゴール**
> - AWS 上にインフラ一式（VPC・EC2・RDS・ECR）が作られている
> - **ネットワーク → サーバー → データベースの順に、1つずつ動作を確認できている**

### 8.0 作るのは一度に、確認は段階ごとに

[CLAUDE.md](../CLAUDE.md) 5章のとおり、新しい環境は**最小の単位で確かめながら**進めます。
ただし今回は、**作るのは一度（`terraform apply` 1回）で、確認を段階に分けます。**

#### なぜ作るのを分けないのか

EC2 の起動スクリプトが RDS の接続先を埋め込んでいるため、
Terraform は「RDS を作ってから EC2」という依存を判断します。
そのため `-target=aws_instance.app` と指定しても RDS が一緒に作られ、
**「EC2 だけ先に作る」ということができません。**

これを分けるには変数でスイッチを設ける必要がありますが、今回は見送りました。
代わりに **CLAUDE.md 5.4 のとおり、確認の順番だけを分けます。**
作る順番は分けられなくても、**確かめる順番は分けられる**からです。

#### 確認の順番

**上から順に確認し、失敗したらそこで止まってください。** 先に進んでも原因が増えるだけです。

| 段階 | 確認すること | 節 | 失敗したときに疑う場所 |
|---|---|---|---|
| **① ネットワーク** | VPC・サブネット・経路が意図どおりか | 8.3 | `network.tf` |
| **② サーバー（EC2）** | SSM で入れるか。Docker とスワップが用意されたか | 8.4 | `ec2.tf`・`iam.tf`・`user_data.sh` |
| **③ データベース（RDS）** | EC2 から接続できるか。外からは接続できないか | 8.5 | `rds.tf`・DB 用セキュリティグループ |
| **④ アプリのデプロイ** | 起動するか。画面が出るか | 9章 | `backend/`・ECR・イメージ |

> **この順番には意味があります。** ネットワークが通っていなければサーバーには入れず、
> サーバーに入れなければデータベースの確認もできません。**土台から順に確かめます。**

### 8.7 （発展）tfstate を S3 に置く

今は `terraform.tfstate` が手元の PC にあります。学習用ならこれで十分ですが、次の弱点があります。

- **PC が壊れると、Terraform がリソースを管理できなくなる**
- 複数人で作業すると、同時 apply で状態が壊れる

実務では S3 に置きます。参考までにコードを載せます（今回は任意）。

```hcl
# versions.tf の terraform ブロックに追加する
terraform {
  backend "s3" {
    bucket = "taskboard-tfstate-＜アカウントID＞" # S3 バケット名は世界で一意である必要がある
    key    = "infra/terraform.tfstate"
    region = "ap-northeast-1"
    encrypt      = true
    use_lockfile = true # S3 だけで排他制御できる（以前は DynamoDB が必要だった）
  }
}
```

**順番に注意**：バケットは Terraform で作る前に存在している必要があるため、先に CLI で作ります。

> **この章のゴール**

### 9.1 なぜ EC2 上でビルドしないのか

`backend/Dockerfile` は Gradle でビルドする2段構えになっています。
しかし **t2.micro（メモリ 1GB）では Gradle のビルドがメモリ不足で失敗します。**

そこで、**ビルドは GitHub Actions（無料）で行い、出来上がったイメージだけを ECR 経由で EC2 に届けます。**
これは実務でも標準的な形（ビルドと実行の分離）です。

```
  開発者が push
       │
       ▼
 GitHub Actions ──── docker build ──── ECR に push
                                          │
                                          ▼
                                 EC2 が docker pull して起動
```

### 9.2 まず手元から1回 push して動作を確かめる

自動化の前に、手作業で1回通してみます。**仕組みを理解するために、この手順は飛ばさないでください。**

Docker Desktop が起動している状態で、リポジトリ直下から実行します。

```powershell
# 1. ECR のリポジトリ URL とレジストリ名を取得する
$ecrUrl = (terraform -chdir=infra/terraform output -raw ecr_repository_url)
$registry = $ecrUrl.Split("/")[0]
echo $ecrUrl

# 2. Docker を ECR にログインさせる
aws ecr get-login-password --region ap-northeast-1 | docker login --username AWS --password-stdin $registry

# 3. イメージをビルドする（backend フォルダを対象にする）
#    --platform を指定する理由：EC2 は x86_64。Windows の Docker も既定で x86_64 だが、明示しておくと安全
docker build --platform linux/amd64 -t "${ecrUrl}:latest" ./backend

# 4. ECR に送る
docker push "${ecrUrl}:latest"
```

ビルドには5〜10分かかります（Gradle の依存ダウンロードのため）。

### 9.5 GitHub Actions で自動化する

手順が通ったら、`main` にマージされたときに自動で ECR へ push されるようにします。

#### 認証方法：OIDC（アクセスキーを GitHub に置かない）

GitHub Actions から AWS を操作する方法は2つあります。

| 方法 | 評価 |
|---|---|
| アクセスキーを GitHub Secrets に入れる | 簡単だが、**永続的な鍵を外部サービスに預けることになる**。漏れたら被害が大きい |
| **OIDC（OpenID Connect）で信頼関係を結ぶ** | **推奨。** GitHub が発行する一時的な身分証明を AWS が検証する。鍵を保存しなくてよい |

OIDC 用のコードは **`infra/terraform/github_oidc.tf` として作成済み**で、8章の `apply` で一緒に作られます。
内容は次のとおりです。

```hcl
# GitHub Actions から、鍵を預けずに AWS を操作できるようにする設定。
#
# 仕組み：
#   GitHub Actions は実行のたびに「私は major182/TaskManegementTool の main ブランチです」
#   という署名付きの身分証（OIDC トークン）を発行できる。
#   AWS 側に「その身分証を持つ者にはこのロールを使わせる」と登録しておけば、
#   永続的なアクセスキーを GitHub に保存せずに済む。

# ※ var.github_repository は variables.tf で定義している
#    （既定値："major182/TaskManegementTool"）

# ---------- GitHub を信頼できる発行元として登録する ----------
resource "aws_iam_openid_connect_provider" "github" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]
}

# ---------- どの条件のときにロールを使わせるか ----------
data "aws_iam_policy_document" "github_assume_role" {
  statement {
    actions = ["sts:AssumeRoleWithWebIdentity"]

    principals {
      type        = "Federated"
      identifiers = [aws_iam_openid_connect_provider.github.arn]
    }

    condition {
      test     = "StringEquals"
      variable = "token.actions.githubusercontent.com:aud"
      values   = ["sts.amazonaws.com"]
    }

    # ★重要★ このリポジトリからの実行だけに限定する。
    # ここを緩めると、他人のリポジトリから自分の AWS を操作できてしまう
    condition {
      test     = "StringLike"
      variable = "token.actions.githubusercontent.com:sub"
      values   = ["repo:${var.github_repository}:*"]
    }
  }
}

resource "aws_iam_role" "github_actions" {
  name               = "${var.project_name}-github-actions"
  assume_role_policy = data.aws_iam_policy_document.github_assume_role.json
}

# ---------- 与える権限：ECR への push だけ（最小権限） ----------
data "aws_iam_policy_document" "ecr_push" {
  statement {
    # ログイン用トークンの取得。リソースを限定できない API のため "*" になる
    actions   = ["ecr:GetAuthorizationToken"]
    resources = ["*"]
  }

  statement {
    actions = [
      "ecr:BatchCheckLayerAvailability",
      "ecr:CompleteLayerUpload",
      "ecr:InitiateLayerUpload",
      "ecr:PutImage",
      "ecr:UploadLayerPart",
      "ecr:BatchGetImage",
    ]
    # このリポジトリにだけ push できる
    resources = [aws_ecr_repository.backend.arn]
  }
}

resource "aws_iam_role_policy" "github_ecr_push" {
  role   = aws_iam_role.github_actions.id
  policy = data.aws_iam_policy_document.ecr_push.json
}

output "github_actions_role_arn" {
  description = "GitHub Actions のワークフローに設定するロール ARN"
  value       = aws_iam_role.github_actions.arn
}
```

8章の `apply` が済んでいれば、ロールはもう出来ています。ARN を確認します。

```powershell
terraform -chdir=infra/terraform output -raw github_actions_role_arn
```

#### ワークフローを追加する

`.github/workflows/deploy.yml` を作ります。

```yaml
# main にマージされたら、バックエンドのイメージをビルドして ECR に送る。
# デプロイ（EC2 への反映）は、事故を防ぐため手動で行う（9.3 の手順）。

name: Deploy backend to ECR

on:
  push:
    branches: [main]
    paths:
      # バックエンドに変更があったときだけ動かす（無駄なビルドをしない）
      - 'backend/**'
      - '.github/workflows/deploy.yml'
  # 手動でも実行できるようにする
  workflow_dispatch:

# OIDC トークンを発行するために必要な権限
permissions:
  id-token: write
  contents: read

env:
  AWS_REGION: ap-northeast-1
  ECR_REPOSITORY: taskboard-backend

jobs:
  build-and-push:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      # アクセスキーではなく OIDC でロールを引き受ける
      - name: AWS の認証
        uses: aws-actions/configure-aws-credentials@v4
        with:
          role-to-assume: ${{ secrets.AWS_ROLE_ARN }}
          aws-region: ${{ env.AWS_REGION }}

      - name: ECR にログイン
        id: login-ecr
        uses: aws-actions/amazon-ecr-login@v2

      - name: ビルドして push
        env:
          REGISTRY: ${{ steps.login-ecr.outputs.registry }}
          # コミットハッシュをタグにする。どのコミットのイメージか後から分かる
          IMAGE_TAG: ${{ github.sha }}
        run: |
          docker build --platform linux/amd64 \
            -t "$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG" \
            -t "$REGISTRY/$ECR_REPOSITORY:latest" \
            ./backend
          docker push "$REGISTRY/$ECR_REPOSITORY:$IMAGE_TAG"
          docker push "$REGISTRY/$ECR_REPOSITORY:latest"
```

最後に、ロール ARN を GitHub に登録します（これは秘密ではありませんが、リポジトリ間で使い回さないよう Secret にしておきます）。

```powershell
gh secret set AWS_ROLE_ARN --body (terraform -chdir=infra/terraform output -raw github_actions_role_arn)
```

### 10.2 DB のバックアップ

**RDS が毎日自動でバックアップを取っています**（保持7日、日本時間の 03:00〜04:00）。


#### それでも手動バックアップを取るべき場面

`terraform destroy`（11章）で **RDS ごと消すと、自動バックアップも一緒に消えます。**
提出後に一度すべて消し、後でまた見せる必要が出そうな場合は、先に SQL として書き出しておきます。

```powershell
# EC2 に入る
aws ssm start-session --target (terraform -chdir=infra/terraform output -raw instance_id) --region ap-northeast-1
```

```bash
# EC2 の中から RDS に対して実行する（PostgreSQL のクライアントを入れる）
sudo dnf install -y postgresql17
source /opt/taskboard/.env
PGPASSWORD="$DB_PASSWORD" pg_dump -h "$DB_HOST" -U "$DB_USER" "$DB_NAME" > /tmp/backup-$(date +%Y%m%d).sql

```

> RDS はプライベートサブネットにあるため、**手元の PC から直接 `pg_dump` はできません。**
> 必ず EC2 を経由します。これは不便ではなく、**インターネットから DB に触れない**という設計どおりの結果です。

### 10.3 費用を止めたいとき

> 合計 約 $5.6／月 は掛かり続けます。**「止めれば $0」ではありません。**
> なお、停止中もデータは消えません（EBS に残ります）。

### 10.4 このプロジェクトでの運用パターン（常時稼働しない前提）

本プロジェクトはスクール課題であり、24時間公開しておく必要がありません。
**触らない時間をどう扱うか**で、次の3段階を使い分けます。

| パターン | 操作 | 月額 | データ | 復帰にかかる時間 | 使う場面 |
|---|---|---|---|---|---|
| **① 起動したまま** | 何もしない | 約 $38 | 保持 | 0秒 | デモ・提出直前の数日 |
| **② EC2 を停止する** | 10.3 の `stop-instances` | 約 $27 | 保持 | 約1分 | その日の作業を終えるとき |
| **③ 全部削除する** | 11章の `terraform destroy` | **$0** | **消える** | 約15分＋デプロイ | 1週間以上触らないとき |

> **② の節約幅が小さい点に注意してください。**
> EC2 を止めても RDS（$18.25／月）は動き続けます。RDS も停止できますが、
> **最大7日で AWS が自動的に再起動する**ため、長期の節約手段にはなりません。
> **1週間以上触らないなら ③ を選んでください。**

**基本方針：「今日の作業終わり」は ②、「しばらく触らない」は ③。**

#### ③ を怖がらなくてよい理由

インフラを全部消すのは、手作業で作っていたら怖い判断です。しかし **Terraform でコードとして持っている以上、`terraform apply` で同じものが再現できます。**
消すことのコストが極端に低い、というのが IaC の実利です（2.2 で説明した「再現できる」という利点が、ここで効いてきます）。

再構築で変わるのは次の2点だけです。

| 変わるもの | 対処 |
|---|---|
| **パブリック IP アドレスが変わる** | `terraform output app_url` で新しい URL を確認し、7.14 の IP 制限はそのまま使える |
| **DB の中身が空になる** | 消す前に SQL として書き出しておく（下記）。RDS の自動バックアップも一緒に消える点に注意 |
| 再構築に時間がかかる | RDS の作成に10分ほどかかるため、合計15分程度みておく |

#### ③ を実行する前のバックアップ

`destroy` すると **RDS の自動バックアップも一緒に消えます。** 残したいデータがあるなら、
10.2 の手順で SQL として書き出し、手元に持ち帰ってから `destroy` してください。

> **もう1つの方法：RDS だけ残す**
> ```powershell
> # EC2 と EIP だけ消す（RDS は残る）
> terraform -chdir=infra/terraform destroy -target=aws_instance.app -target=aws_eip.app
> ```
> この場合の月額は RDS の $21 程度になります。$0 にはなりませんが、**データを失わずに済みます。**
> 「来週また触る」ならこちらのほうが手間がかかりません。

#### 復帰させる手順

```powershell
# 1. インフラを作り直す（約5分）
terraform -chdir=infra/terraform apply

# 2. 新しい URL を確認する
terraform -chdir=infra/terraform output -raw app_url
```

イメージは ECR に残っているので、EC2 は起動時に自動で `docker pull` します（`user_data.sh` の処理）。
**バックアップから戻す場合**は、サーバーに入って次を実行します。

```bash

source /opt/taskboard/.env
PGPASSWORD="$DB_PASSWORD" psql -h "$DB_HOST" -U "$DB_USER" -d "$DB_NAME" < backup.sql
```

> **💡 ECR だけは消さずに残す、という選択もあります。**
> ECR の保管料は月 $0.10 程度とごくわずかです。`terraform destroy` は ECR も消しますが、
> イメージを残しておけば復帰時のビルド（5〜10分）を省けます。
> その場合は `terraform destroy -target=aws_instance.app -target=aws_eip.app` のように
> **対象を指定して部分的に消す**こともできます（EC2 と EIP だけ消えて、月額は $0.10 になります）。

## 12. フロントエンド（React）の配信：バックエンドに同梱する

**決定：`npm run build` の成果物を Spring Boot に同梱し、1つのコンテナで配信します**（案A）。
Issue #48 はこれで決着です。

### 12.1 なぜ同梱にしたか

| 案 | 内容 | 費用 | 判定 |
|---|---|---|---|
| **A. バックエンドに同梱** | ビルド成果物を Spring Boot の `src/main/resources/static/` に入れ、1コンテナで配信 | **追加 $0** | **◯ 採用** |
| B. S3 ＋ CloudFront | 静的ファイルを S3 に置き、CloudFront で配信。`/api/*` を EC2 へ転送 | 月 $1 未満 | ✕ 今回は見送り |
| C. Amplify Hosting | Git 連携で自動ビルド・デプロイ | 月 $1 程度 | ✕ IaC で管理する意義が薄い |

**採用の理由**

1. **まずシンプルな構成で動かすことを優先する。** 段階を1つずつ確かめながら進める方針（8.0）に合う。
   配信経路が増えるほど、問題が起きたときの切り分けが難しくなる
2. **画面と API が同じドメインになる。** CORS の許可設定も、CSRF トークンを画面側から読むための
   手当ても**一切不要**になる（[02 技術選定書 5.1](02_tech-stack.md) が前提としている構成そのもの）
3. **インフラの変更が要らない。** Terraform は今のままでよく、EC2 1台で完結する
4. **スクール教材でも S3 ＋ CloudFront は使わない**と解説されていた

### 12.2 この選択で諦めること

正直に書いておきます。

| 諦めること | 影響 |
|---|---|
| **HTTPS にできない** | EC2 に直接 HTTP でつなぐため、セッション Cookie の `Secure` 属性が働かない。学習用かつアクセス元を自分の IP に限定しているため、今回は許容する |
| CDN による高速化 | 利用者が自分だけなので影響はない |
| 画面だけの更新でもバックエンドを再デプロイ | イメージを作り直して push し直す必要がある |

将来 B に移行したくなった場合、**インフラ側の変更は「S3 ＋ CloudFront を足す」ことと、
セキュリティグループの許可元を CloudFront に変えること**の2つです。
アプリのコードはほぼそのまま使えます。

> **B に移行する場合、7.14 の IP 制限とぶつかります。**
> CloudFront は AWS 側のサーバーから EC2 へ通信するため、自分の IP だけを許可していると
> **CloudFront からの通信が届かず、画面が表示できません。**
> そのときは許可する送信元を「自分の IP」から「CloudFront からの通信のみ」に切り替えます
> （`com.amazonaws.global.cloudfront.origin-facing` という AWS 管理のプレフィックスリストを使います）。

### 12.3 実現方法（段階④で実施）

インフラには影響しないため、**アプリのデプロイ（9章）と同じタイミング**で対応します。
具体的な作業は次のとおりで、これは別の Issue として扱います。

| やること | 内容 |
|---|---|
| フロントエンドをビルドする | `frontend/` で `npm run build` → `dist/` ができる |
| Spring Boot に入れる | `dist/` の中身を `backend/src/main/resources/static/` に配置する |
| 画面を返す経路を用意する | React Router を使うため、`/api/**` 以外のパスは `index.html` を返すようにする |
| `Dockerfile` を直す | 1段目でフロントエンドもビルドするか、CI で作った `dist` を受け取る |
| Spring Security の設定 | 静的ファイル（`/`、`/assets/**`）は認証なしで返す |

> **注意：React Router を使っているため、`/boards/123` のような URL を直接開くと
> Spring Boot が 404 を返します。** サーバー側に該当するパスが無いためです。
> `/api/**` 以外は `index.html` を返す設定が必要になります。初見で必ずつまずく箇所です。

## 13. つまずきポイント早見表

| 症状 | 原因 | 対処 |
|---|---|---|
| コンソールにリソースが表示されない | 見ているリージョンが違う | 画面右上で「東京」を選ぶ |
| `AgentToolkit is only available in us-east-1` | `aws agent-toolkit` は東京リージョンでは動かない | `--region us-east-1` を付ける（5.5） |
| `aws` の出力が `cp932 codec can't encode` で落ちる | 日本語 Windows の文字コードで、記号が扱えない | `--query` で必要な項目だけ取り出す（例：`--query "skills[].name" --output text`） |
| `terraform apply` で権限エラー | IAM ユーザーの権限不足 | `AdministratorAccess` が付いているか確認 |
| `plan` に `-/+` が出た | リソースが作り直される＝**データが消える** | apply せずに原因を調べる。`user_data` の変更が典型 |
| ブラウザで開けない | ①**アクセス元の IP が許可されていない** ②コンテナが起動していない ③まだ起動中 | **まず 7.14 で IP を確認・更新** → `docker compose ps` → 3分待つ |
| 昨日まで開けたのに今日は開けない | 回線のグローバル IP が変わった（最も多い原因） | 7.14 の手順で `allowed_app_cidr` を更新して `apply` |
| 外出先・スマホから開けない | 設定どおりの動作（自分の回線の IP のみ許可しているため） | その場所の IP を追加するか、一時的に公開範囲を広げる（7.14） |
| アプリが起動直後に落ちる | メモリ不足（OOM Killer） | `free -h` でスワップを確認。`dmesg \| grep -i kill` で確認 |
| アプリが DB につながらない | ①RDS がまだ作成中 ②SG の設定 ③`.env` の値 | `aws rds describe-db-instances --db-instance-identifier taskboard-db --query "DBInstances[0].DBInstanceStatus"` が `available` か確認 |
| 手元の PC から DB につなげない | 設計どおり（RDS はプライベートサブネットにあり外部から到達できない） | EC2 を踏み台にする（10.2） |
| `apply` が10分以上終わらない | RDS の作成には通常10分ほどかかる | 待つ。15分を超えたらコンソールでイベントを確認 |
| `destroy` で RDS が消せない | `deletion_protection = true` になっている | `terraform.tfvars` で `false` にして `apply` してから `destroy` |
| `docker compose` が見つからない | user_data の実行が未完了 | `sudo tail -f /var/log/cloud-init-output.log` で進捗を見る |
| SSM で接続できない | エージェントの登録待ち、または IAM ロール未付与 | 3分待つ。`aws ssm describe-instance-information` で登録を確認 |
| ECR の push で `denied` | ECR へのログインが切れている（12時間で失効） | `aws ecr get-login-password ...` をやり直す |
| destroy 後も課金される | Elastic IP や EBS が残っている | 11.2 の確認コマンドを実行し、残っていれば手で削除 |
| tfstate を消してしまった | Terraform が管理対象を見失った | コンソールで手動削除するか、`terraform import` で取り込み直す |
